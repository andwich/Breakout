## Revised Creative Direction

Adopt the reference’s apparent product aesthetic:

- Dark, neutral workspace background instead of a saturated neon arcade backdrop
- Large rounded panels with subtle borders, restrained shadows, and spacious layout
- Functional, information-dense UI: clearly visible model/run state, performance metrics, active modifiers, and event feed
- Accent color used sparingly for state—green for positive/ready, amber for warnings, red for failure/damage, and one primary brand accent
- Smooth, confidence-building transitions rather than constant pulsing/glow effects

This means replacing the current global `NEONCYAN`, `NEONMAGENTA`, and related rainbow-oriented theme constants with a semantic palette: `SURFACE`, `PANEL`, `TEXT_PRIMARY`, `TEXT_MUTED`, `ACCENT`, `SUCCESS`, `WARNING`, and `DANGER`. The project presently centralizes colors in `autoload/gametheme.gd`, making that the correct first integration point.[1]

## Gameplay Reframe

Rather than copying a game mechanic from the video, borrow its **operational feedback model**:

| Current element | Revised treatment |
|---|---|
| Score | “Run output” or run score, shown as a prominent but calm metric |
| Lives | Stability / retries, shown as discrete status indicators |
| Power-ups | Active modules with name, icon, duration, and concise effect description |
| Combo | Throughput / momentum meter, with a small event log |
| Brick destruction | A processed job/task, with compact confirmation feedback |
| Level | Workload or scenario, with an explicit stage label |

The existing HUD already tracks score, lives, multiple timed effects, phase messaging, and level intros; revise `ui/hud.gd` and its scene layout rather than creating a second parallel UI system.[1]

## Presentation Changes

1. **Palette and typography**
   - Replace the neon color-cycle title treatment with a sober dashboard-like title screen.
   - Use a monospaced or technical UI font for metrics and labels, with a clean sans-serif for primary headings.
   - Remove nonessential rainbow animation and reserve animation for state changes.

2. **Panel-based HUD**
   - Split the HUD into stable panels: run status, active modules, performance/combos, and controls.
   - Make timers resemble task progress bars or token-generation-style activity indicators.
   - Preserve `GameState.Phase` as the source of truth; the HUD should only render it.[1]

3. **Impact feedback**
   - Replace large glow bursts with a brief “execution” flash, compact particle fragments, and a structured event entry such as `BRICK REMOVED +250`.
   - Keep screen shake minimal and use short hit-stop only for valuable/destructive interactions.
   - Retain the existing audio pooling and synthesized effects, but retune tones toward soft mechanical clicks, subtle confirmation chimes, and restrained error buzzes.[1]

4. **Background**
   - Replace the arcade-starfield feel with a deep charcoal canvas, subtle grid/noise texture, and slow-moving data-line or terminal-like background elements.
   - Make the playfield border feel like a contained workspace/canvas, not a glowing arcade cabinet.

## Mechanics Worth Adding

The reference suggests a “tooling workflow” feel more than a new arcade mechanic. Use that as a theme layer on top of the existing power-up architecture:

- **Loadout before a run:** Select 2–4 modules before starting—e.g., multiball, laser, sticky paddle, wider paddle.
- **Module upgrades between levels:** Present three concise choices after round clear, such as “Laser: +1 beam,” “Ball: +10% speed,” or “Paddle: wider catch window.”
- **Run telemetry:** Track destruction rate, best combo, accuracy/recovery time, active effects, and current multiplier.
- **Event stream:** Add an optional compact log for major actions: module enabled, brick destroyed, level completed, life lost.
- **Configurable presets:** Add `Casual`, `Precision`, and `Endless` configurations via level/run definitions rather than hard-coding different behavior paths.

The existing `PowerUpRegistry`, level drop weights, and phase-driven transition flow are suitable foundations for this without rewriting the ball, paddle, or brick systems.[1]

5. **Kill/reuse tweens.** Any changed effect must retain a member reference to its tween, kill it before replacing it, and clean it up during `_exit_tree()`.[1]
