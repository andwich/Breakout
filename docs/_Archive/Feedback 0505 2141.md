## Gameplay Mechanics

**Ball physics feel**

The current `velocity.bounce(normal)` is correct for flat surfaces, but the paddle reflection formula has a subtle issue. In `ball.gd`, after a paddle hit you set velocity to `aim * velocity.length()`, but then immediately fall through to the minimum-speed clamps and `velocity.normalized() * speed`, which *discards* the length variation from `velocity.length()`. Effectively the ball always exits at exactly `speed` regardless of how it hit. That's fine for consistency, but it means you never get organic speed-up from glancing hits. Worth deciding intentionally.

The minimum velocity guards (`absf(velocity.y) < 50.0`) are good, but they only clamp to sign — they don't add the delta to the other axis to conserve speed, so you subtly slow the ball on near-horizontal shots.

**`_configure_brick` references `cols` which doesn't exist**

In `level_builder.gd`, `_configure_brick` uses `cols / 2` and `cols / 2 - 1` — but `cols` is a local variable in `build_level`, not a member of `LevelBuilder`. This is a runtime error: the method receives `config` but doesn't receive `cols`, so it reads a nonexistent variable. Fix: pass `cols` as a parameter, or derive it inside the method from `config["cols"]`.

```gdscript
# current (broken)
if config.get("boss_hp", 0) > 0 and row == 0 and (col == cols / 2 or col == cols / 2 - 1):

# fix
var cols: int = config.get("cols", 8)
if config.get("boss_hp", 0) > 0 and row == 0 and (col == cols / 2 or col == cols / 2 - 1):
```

**Laser collision mask mismatch**

`laser_beam.tscn` has `collision_mask = 5` (layers 1+4: paddle + powerup), but it should be `collision_mask = 4` (layer 3: brick). Layer 5 in `project.godot` is "laser", and bricks are on layer 3. The laser uses `Area2D` with `body_entered`, so the mask must include brick's layer (3 → bit 4 = value 8 in 1-indexed layer notation... actually in Godot 4, layer 3 = value `4`, layer 4 = value `8`). Current mask of `5` = layers 1 and 3, which would hit paddle too. Should be `4` for bricks only.

**Slow ball restore on multiball**

In `_apply_slow_balls`, you store speeds by `get_instance_id()` and restore them later. But `spawn_ball` during the slow period creates new balls with `base_speed * 0.6` (because that's what multiball clones get from `original.velocity`... actually no, clones inherit velocity, not speed). Actually the new ball's `.speed` field is set from `LevelDefs.config_for_level(current_level)["speed_mult"]` at full speed — but then `_restore_ball_speeds` only restores balls that are in `_original_ball_speeds`. Balls spawned *during* a slow period won't be in the dict, so they keep full speed while others are slow. Minor but perceptible. Fix: apply the slow factor in `spawn_ball` if `_slow_timer` is running, or restore all balls uniformly.

**`complete_level` race condition**

`complete_level` uses `await get_tree().create_timer(1.8).timeout`. If the player somehow destroys the last brick twice (edge case from simultaneous ball/laser collision), `complete_level` can be called twice, starting two async chains both incrementing `current_level`. Recommend gating with a boolean flag or checking phase before incrementing:

```gdscript
func complete_level() -> void:
    if phase != GameState.Phase.PLAYING:
        return  # already handling completion
    phase = GameState.Phase.PAUSED
    ...
```

**Aim control angle**

`aim_angle = clampf(velocity.x / speed * 45.0, -45.0, 45.0)` — this works but note it's derived from `velocity.x` which is always `direction * speed` (full speed or zero), so aim snaps between 0 and ±45 with no intermediate when using keyboard. Mouse movement would need explicit tracking for analogue feel. This is fine for keyboard-first but worth noting.

**Lives container only supports 5 hearts**

The HUD hard-codes 5 `Heart` nodes. If `EXTRA_LIFE` is collected more than twice (starting with 3), the 6th heart won't display — `update_lives` iterates `hearts.size()` which is fixed at 5. Add an overflow label or dynamically add heart nodes.

## Aesthetics

**Shader effectiveness**

`brick_glow.gdshader` samples `TEXTURE` at UV offsets — but `ColorRect` nodes don't have a meaningful texture (it's a solid color). The shader will just add `glow_color * 0.25 * glow_intensity` to the base color, which gives a flat color shift rather than an actual glow. For a real glow on a `ColorRect`, you'd want to use the UV distance from the rect's edges to create an inner/outer glow effect, or switch brick sprites to `TextureRect` with a small base texture.

**Ball trail particles**

The `Trail` particle has `direction = Vector3(0, 1, 0)` (downward in 3D coords = upward in 2D Y-down), which is the right idea. But `spread = 5.0` is very tight and `lifetime = 0.2` is short, making the trail almost invisible at high speed. Suggest `spread = 15.0`, `lifetime = 0.35`, and setting the particle color to match the ball's neon yellow (`Color(1, 1, 0.6, 0.5)`) for a more visible streak.

**Brick modulation conflict**

The `_update_visual` in `brick.gd` sets `modulate.a` (alpha falloff as HP decreases) at the end — but for boss/metal bricks, this fights with the visual weight their shader is supposed to convey. A boss brick at 1 remaining HP becomes 60% transparent, making it look weaker than a fresh standard brick. The alpha fade is a nice mechanic cue for standard bricks but should be skipped for boss/metal types:

```gdscript
if brick_type == "standard":
    var alpha := 1.0 - float(max_hp - _hp) / max_hp * 0.4
    modulate.a = alpha
```

**Paddle aim indicator** 

The `_draw()` method in `paddle.gd` draws aim lines only during sticky mode. Extending this to always show a subtle aim indicator when the ball is waiting (even pre-launch) would dramatically improve game feel — players would have visual feedback for where the ball will go before launching. Use low alpha (`0.15`) lines continuously when `phase == READY`.

**HUD layout on large screens**

At 1280×720, the score is at `x=16` and high score at `x=840` with lives at `x=1100`. There's a big empty zone in the center-left. The level label at `x=540` is mid-centered, but nothing occupies `x=200–540`. Tightening this into a proper centered top bar would feel more polished.

**Background is a flat fill**

`RenderingServer.set_default_clear_color(GameTheme.NEON_BG)` gives the dark purple-black background, but there's no scanline or grid overlay on the background itself. A subtle dot grid or very faint horizontal scanline at the background level (via a full-screen `ColorRect` with the scanline shader at very low intensity) would sell the retro-neon aesthetic much more strongly.

## Priority order for fixes

The `cols`-out-of-scope bug in `level_builder.gd` is the most critical — it will crash on any level with boss bricks (levels 3–5 and endless). Everything else is either a minor logic gap or a polish opportunity.

After patching the bugs, the two highest-impact aesthetic improvements are the **aim indicator extension** (zero-cost, huge game feel improvement) and the **boss brick alpha fix** (one line, eliminates a confusing visual). The glow shader on `ColorRect` is worth reworking but requires more effort — a quick interim fix is replacing the UV-offset approach with a simple edge-distance glow in fragment:

```glsl
void fragment() {
    float edge = min(min(UV.x, 1.0 - UV.x), min(UV.y, 1.0 - UV.y));
    float glow = smoothstep(0.0, 0.15, edge);
    COLOR = mix(glow_color * glow_intensity, COLOR, glow);
    COLOR.a = 1.0;
}
```

This creates an actual inner glow that's bright at the edges and fades toward center — much more legible on a `ColorRect`.
