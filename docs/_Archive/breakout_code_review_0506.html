Play mechanisms

1

Velocity clamp → renormalize → clamp loop never converges

After Y is clamped and renormalized, X is clamped and renormalized again — which shrinks Y back below 50. Each pass undoes the previous one. Fix: clamp both components once, after a single normalization, without renormalizing again.

entities/ball.gd _physics_process (bounce branch)

Critical
2

complete_level() can fire twice during 1.8s transition

The guard checks phase != PLAYING, but phase stays PLAYING during the await. If two bricks are destroyed in the same tick (ball + laser), brick_count hits 0 twice and complete_level is called a second time before the first await yields. Add _transitioning to the guard.

main.gd complete_level()

Critical
3

Ball scores only on destroy — multi-HP bricks feel unresponsive

brick_hit.emit is gated on is_queued_for_deletion(), so standard ball hits on metal/boss bricks give zero score feedback. Laser awards 5 pts per hit; ball gives nothing. Even a small per-hit award (1–2 pts) would close the asymmetry and give feedback.

entities/ball.gd _physics_process, vs laser_manager.gd

Significant
4

Multiball clones miss brick_hit connection

spawn_ball() wires brick_hit and life_lost correctly. But the multiball path sets clone.launched = true and velocity directly, bypassing Ball.launch() — so the clone never follows the sticky paddle check. Low risk now, but if a sticky is active when multiball fires, the stuck ball's launch logic mismatches.

main.gd _on_powerup_collected MULTIBALL

Significant
5

_on_ball_lost lives can go below zero

If multiple balls exit near-simultaneously, has_active_ball() may return false for each, decrementing lives more than once. Clamping to max(0, lives - 1) or adding a guard flag prevents a negative-life game-over cascade.

main.gd _on_ball_lost

Significant
6

Laser lambda captures freed node

The body_entered lambda calls laser.queue_free() then reads body.is_queued_for_deletion() and body.point_value after. If the brick is also freeing in the same frame, body.point_value is read from a freed object. Use a local var pts = body.point_value before any queue_free() call.

entities/laser_manager.gd _fire_laser lambda

Significant
7

has_method("take_damage") check is dead code

Every Brick always has take_damage, so the else branch (collider.destroy()) never runs. The check adds noise and could hide bugs if a non-Brick body somehow passes the is Brick check. Remove the conditional; call take_damage directly.

Launch / scene

8

Wall collision shapes are centered on edge, not inside

LeftWall at position = (0, 360) with a 20px wide shape spans x = −10 to x = 10. Half the wall body is off-screen. A ball at x=8 could be on-screen but past the collision edge. Move each wall inward by half its thickness: LeftWall → x=10, RightWall → x=1270, TopWall → y=10.

main.tscn LeftWall / RightWall / TopWall positions

Significant
9

Bricks freed mid-level may fire destroyed signal after reset

_reset_round_nodes() calls queue_free() on all bricks, but if a brick already called destroy() that frame, its destroyed signal is still in the queue. When it fires, _on_brick_destroyed decrements brick_count (clamped to 0) and calls complete_level() on the new level's bricks. Guard: check _transitioning in _on_brick_destroyed.

main.gd _reset_round_nodes, _on_brick_destroyed

Significant
10

Ball VisibleOnScreenNotifier fires even when walls contain the ball

With walls in place the ball should never exit sides or top, but the notifier still calls queue_free() on any screen exit — no life penalty. Consider disconnecting the notifier for non-bottom exits entirely, or adding a specific bottom-only guard before the free.

Aesthetic

11

Trail particles always travel downward, ignoring ball direction

The GPUParticles2D direction is (0,1,0) in world space. Particles go down regardless of ball velocity — a ball moving upward shows its trail ahead of it, not behind. Set local_coords = true and direction to (0,1,0) relative to ball, or update direction in _physics_process to match -velocity.normalized() as a 3D vector.

entities/ball.tscn Trail ParticleProcessMaterial

Critical
12

victory.tscn — HighScoreLabel visible by default with empty text

The node has no visible = false in the tscn, so on first launch (no saved score) it renders an empty label that takes up layout space. victory.gd only sets visibility when high > 0. Add visible = false to the tscn node, or guard high_score_label.visible = false at the start of _ready().

ui/victory.tscn HighScoreLabel, ui/victory.gd _ready()

Significant
13

Aim indicator only shows when moving — invisible in static ready state

The paddle's _draw() checks absf(aim_angle) > 2.0, so a stationary paddle shows no launch guide. Players launching straight up get no visual cue. Show a default vertical guide (angle = 0) whenever phase == READY and a ball is waiting.

entities/paddle.gd _draw()

Significant
14

Ball _draw() uses no queue_redraw() — circle is drawn once

Godot calls _draw() once at scene start and caches it. Since the circle never changes, this is actually fine visually. But note: if you ever add dynamic color (e.g. flash on damage), you'll need queue_redraw() after the state change. Worth a comment in code to avoid future confusion.

15

No score flash or sound hook on brick hit

_on_brick_hit silently increments score with no screen feedback. A brief score-delta popup (+10 floating upward from the brick) and/or a placeholder AudioStreamPlayer call would make every hit feel rewarding. Even an empty AudioStreamPlayer node wired to _on_brick_hit keeps the hook in place for SFX later.
