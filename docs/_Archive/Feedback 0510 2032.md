## 🔴 Critical Bugs

### 1. Laser persists across level transitions — `main.gd :: _load_level()`

`_load_level()` calls `paddle.reset()`, `_slow_timer.stop()`, and clears balls — but **never calls `laser_manager.deactivate()`**. Clear Level 1 with an active Laser powerup and the laser keeps auto-firing into Level 2's intro and beyond. `_start_new_run()` does deactivate it, but that path is only hit on full restart.

**Fix:** Add `laser_manager.deactivate()` as the first line in `_load_level()`, before `_slow_timer.stop()`.

---

### 2. Multiball race condition — `_on_ball_lost()`

With Multiball active, several balls can exit the screen in the same physics frame. Each triggers `life_lost` → `_on_ball_lost()`. The guard `if _has_active_ball(): return` reads the balls container, but since `queue_free()` is deferred in Godot 4, multiple calls in the same frame can all see the same "no active balls" state and each decrement lives independently — potentially killing the player in one frame.

**Fix:** Add a `_life_lost_this_frame: bool` flag reset in `_physics_process` or use a deferred single-fire pattern:

```gdscript
var _life_lost_pending := false

func _on_ball_lost() -> void:
    if phase in [...]:
        return
    if _has_active_ball():
        return
    if _life_lost_pending:
        return
    _life_lost_pending = true
    call_deferred("_process_life_loss")

func _process_life_loss() -> void:
    _life_lost_pending = false
    lives = max(0, lives - 1)
    hud.update_lives(lives)
    if lives <= 0:
        _enter_game_over()
        return
    _reset_round_after_life_loss()
```

## 🟠 Significant Issues

### 3. Redundant level prefix in subtitle — `main.gd :: _level_subtitle_text()`

The level intro panel shows two lines:
- Title: `"LEVEL 1  ·  OPENING VOLLEY"`
- Subtitle: `"LEVEL 1  —  Learn the rebound angle and settle into the pace."`

The subtitle prefixes `"LEVEL X  —  "` but the title already contextualizes the level. The subtitle should be the teaching text only.

**Fix:**
```gdscript
func _level_subtitle_text() -> String:
    var config := LevelDefs.config_for_level(current_level)
    return str(config.get("intro_text", ""))
```

---

### 4. `Vector2.ZERO` used as spawn sentinel — `_spawn_ball()`

```gdscript
func _spawn_ball(at: Vector2 = Vector2.ZERO) -> Ball:
    if at == Vector2.ZERO:
        at = paddle.global_position + Vector2(0, -30)
```

If the paddle ever legitimately occupies (0,0) (e.g. during initialization before position is set), the ball would snap to paddle instead of the intended position. It's also semantically opaque.

**Fix:** Use a nullable pattern or a dedicated sentinel constant:
```gdscript
const _NO_POS := Vector2(-99999, -99999)
func _spawn_ball(at: Vector2 = _NO_POS) -> Ball:
    if at == _NO_POS:
        at = paddle.global_position + Vector2(0, -30)
```

---

### 5. Power-up effects aren't fully cleared on level load

`_load_level()` calls `paddle.reset()` (clears big paddle + sticky timers) and `_slow_timer.stop()`, but doesn't clear the HUD effect rows until `hud.clear_all_effect_timers()`. If the Laser effect bar was mid-countdown, it's cleared visually, but the underlying `LaserManager` timer was never stopped (see issue #1). These two bugs compound.

More subtle: `hud.clear_all_effect_timers()` kills tweens but if a tween callback fires **just after** `clear_effect_timer` runs (edge case during level transition), it would call `clear_effect_timer(effect_id)` on a row that was already removed, which is harmless due to the early-return guard — but still worth noting as a timing fragility.

---

### 6. Title screen power-up legend overflows on one line

In `title_screen.gd`:
```gdscript
powerup_legend.text = "  ".join(lines)
```

Six entries joined on one line at font_size 14 likely overflows the 600px container. `autowrap_mode = 2` is set, which will wrap, but the result is inconsistent (wraps at arbitrary points based on container width). 

**Fix:** Use `"\n".join(lines)` or a 2-column layout (3 entries per row):
```gdscript
var left := lines.slice(0, 3)
var right := lines.slice(3)
powerup_legend.text = "\n".join(left) + "    " + "\n".join(right)
```
Or better, format into two columns with tab-separated pairs.

## 🟡 Gameplay / Feel Issues

### 7. Ball collision mask includes layer 4 (powerup bitmask = 8) — it doesn't, but wall layer is 6

`ball.tscn` has `collision_mask = 37` = binary `100101` = layers 1, 3, 6 (paddle, brick, wall). Wall is layer 6 per `project.godot`. This is correct. However, `LeftWall`, `RightWall`, and `TopWall` in `main.tscn` have `collision_layer = 32` (layer 6). Layer 6 bit = 2^5 = 32. ✓ The walls are fine, but the `PlayfieldBorder` draws its rect starting at `(0, 0)` — exact screen edge — while the wall *centers* are at x=10 and x=1270 with 20px width, meaning the wall inner edges are at x=0 and x=1280. The border line at x=0 sits behind the wall. Visually fine, but if the window is ever resized dynamically, the border redraws (via `size_changed`) but the wall positions are baked in at 1280×720 — they'd be misaligned.

---

### 8. Sticky paddle aim lines show when no ball is present

In `paddle.gd :: _draw()`:
```gdscript
var draw_aim := show_aim and (
    (stuck_ball and is_instance_valid(stuck_ball) and sticky_mode) \
    or (not stuck_ball)
)
```

When `sticky_mode = true` and `stuck_ball = null` (no ball caught yet), `not stuck_ball` is `true`, so aim lines render. This is correct. But once a ball is stuck, aim lines draw from the "stuck ball will go here" position. When the ball is launched but before a new one arrives, `stuck_ball = null` so aim lines re-appear immediately — before `show_aim` would normally be true in READY phase. This is a minor UX jitter.

**Minor fix:** Also gate on `show_aim` being true (it already does), so this resolves itself when `show_aim` is cleared during PLAYING phase. Actually the existing code is fine — `show_aim` is set false during `_launch_waiting_ball`. This is OK.

---

### 9. `_resolve_round_clear` only triggers victory at exactly level 5

```gdscript
if current_level == 5:
    ...victory...
```

This means if `RunState.start_level` is ever set to a value > 5 and the player clears level 5 again somehow (impossible via normal flow, but worth noting), there's no issue. What IS worth noting: if a player somehow ends up at current_level = 5 via endless mode bookkeeping errors, this triggers victory unexpectedly. Low risk but `>= 5` or an explicit `base_level_count` constant would be more robust:

```gdscript
const BASE_LEVEL_COUNT := 5
if current_level >= BASE_LEVEL_COUNT:
```

---

### 10. Brick particle `one_shot` fires correctly for hits but `destroy()` duplicate has no cleanup

In `brick.gd :: destroy()`:
```gdscript
var vfx := _particles.duplicate()
vfx.emitting = true
vfx.one_shot = true
get_tree().root.add_child(vfx)
vfx.global_position = global_position
```

The duplicated particle node is added to root but **never freed after playback**. A `timer` or `finished` signal should clean it up:

```gdscript
var vfx := _particles.duplicate()
vfx.emitting = true
vfx.one_shot = true
vfx.finished.connect(vfx.queue_free)   # ← add this
get_tree().root.add_child(vfx)
vfx.global_position = global_position
```

Without this, every destroyed brick leaves an orphaned GPUParticles2D node in the scene tree. Over a full run of 5 levels with ~200 bricks this is a mild memory/scene-tree leak.

## 🟢 Aesthetic Polish

### 11. HUD `HighScoreLabel` positioning is cramped

In `hud.tscn`, `HighScoreLabel` sits at offset_left=720, right=920, which puts it between the `LevelLabel` (440–640) and the right edge. At font_size=16 it fits, but "HIGH: 99999" is tight. Consider anchoring it to the right edge like `LivesContainer`:

```
anchor_left = 1.0, anchor_right = 1.0
offset_left = -200.0, offset_right = -200.0  # right of LevelLabel
```

Or display it below the score label on the left side, which is more conventional.

---

### 12. Boss pulse uses `tween_method` but tween is never killed on destroy

In `brick.gd :: _ready()`:
```gdscript
var tween := create_tween()
tween.set_loops()
tween.tween_method(func(v): _shader_mat.set_shader_parameter("glow_intensity", v), 1.5, 3.0, 0.6)
```

When `destroy()` calls `queue_free()`, the node's tweens are automatically stopped — Godot 4 ties `create_tween()` tweens to the node. So this is actually fine. ✓ Just worth confirming.

---

### 13. `_level_title_text()` uppercases the authored name

```gdscript
return (prefix + authored).to_upper()
```

This works for ASCII but would mangle accented characters. Fine for the current level names, just a future-proofing note.

---

### 14. Ball speed uses `base_speed * speed_mult` but slow applies `* 0.6` of `base_speed`, not of the level speed

In `_spawn_ball()`:
```gdscript
ball.speed = ball.base_speed * LevelDefs.config_for_level(current_level)["speed_mult"]
if not _slow_timer.is_stopped():
    _original_ball_speeds[ball.get_instance_id()] = ball.speed
    ball.speed = ball.base_speed * 0.6   # ← uses base_speed, not leveled speed
```

On Level 5 (speed_mult=1.45), the "slow" speed is 0.6× base = 60% of level 1 speed, but 41% of the level 5 speed. At higher levels this is actually correct (slow should feel the same), but it means slow balls in level 5 are slower than the intended 60%-of-current relative to current speed. If the intent was "60% of current level speed," change to `ball.speed * 0.6`. Design call either way — just worth being intentional.
