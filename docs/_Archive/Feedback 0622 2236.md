Each call to `_show_combo` creates a NEW tween (`tw := create_tween()`) without killing any previous tween from a prior `_show_combo` or `_reset_combo` call. So if combo events happen rapidly (chained brick destructions within the same 0.6s combo window), multiple overlapping tweens could be animating `_combo_label.scale` and `modulate:a` concurrently. Since `create_tween()` on the same node doesn't automatically cancel previous tweens targeting the same properties (Godot allows multiple independent Tween objects to run concurrently and they'll just "fight" — last-write-wins per process frame, causing flicker/jank), this is a real potential bug: rapid combo increments could cause the label to flicker between fade-out (from an old tween's delayed fade) and the bounce-in scale of a new tween, or the modulate alpha snapping unexpectedly to 0 mid-animation from an earlier `tween_delay(0.3)` firing after a NEWER combo bump should have kept it visible.

Let's trace concretely: Player hits 2 bricks in quick succession (0.1s apart), combo count goes 3→4.
- t=0.00: `_show_combo(3, ...)` creates tw1: scale animates 1.4→1.0 over 0.15s (bounce), parallel modulate:a tween with `set_delay(0.3)` then animates to 0 over 0.5s — so this fade actually starts at t=0.3 and finishes at t=0.8.
- t=0.10: `_show_combo(4, ...)` creates tw2: resets `_combo_label.scale = Vector2(1.4,1.4)` (already set directly, not animated) then tw2 animates scale 1.4→1.0 over 0.15s (finishes t=0.25), and ALSO creates a new parallel modulate:a tween with delay 0.3 (starts fading at t=0.4, ends t=0.9).

Now we have TWO modulate:a tweens running concurrently: tw1's fade (active t=0.3 to t=0.8) and tw2's fade (active t=0.4 to t=0.9). Between t=0.3 and t=0.4, tw1's fade is actively driving alpha downward toward 0, while tw2 hasn't started yet (still in its delay phase) — but tw2's existence doesn't override tw1; they both are valid tweens that will both eventually write to `modulate:a`. At t=0.4, tw2 starts also writing to modulate:a, racing with tw1's still-active fade (until t=0.8). Two tweens simultaneously writing to the same property each frame will produce visibly glitchy/non-monotonic alpha changes (each Tween calculates its own eased value independently and assigns it, so whichever tween's `tween_property` step runs LAST in that frame "wins" for that frame, but next frame the other might win, causing flicker).

So yes — **this is a real, reproducible bug**: rapid combo updates create overlapping competing tweens on `modulate:a` (and to a lesser extent on `scale`), causing potential flicker/visual jank during fast combo chains (which is exactly the most exciting moment, e.g., multiball clearing several bricks rapidly). The fix: kill any existing combo-tween before creating a new one — store the tween(s) in a member variable and call `.kill()` if valid before starting new ones, mirroring the pattern already used elsewhere in the codebase (e.g., `_score_tween` in hud.gd, `_shake_tween` in main.gd). I should provide a corrected snippet.

This matches the memory's "on the horizon" note: "combo fade-out tween racing with bounce-in animation" — confirmed STILL PRESENT, and I've now precisely diagnosed the mechanism (overlapping Tween objects on the same property across rapid combo increments), which is more precise than the vague description in memory. ## 🔴 Critical — Endless Mode launch skips one-time setup

In `main.gd`, `_ready()` branches on `RunState.start_level`:

```gdscript
func _ready() -> void:
	if RunState.start_level > 1:
		start_new_run(RunState.start_level)
	else:
		_run_setup()
		_start_new_run(current_level)
```

`start_new_run()` only calls `_start_new_run()` — it **never calls `_run_setup()`**. That means every time `main.tscn` loads with `start_level > 1` (i.e. every entry into Endless Mode from the Victory screen, since that's a fresh scene load), the following never happens:

- `laser_manager.set_paddle()`, its `brick_scored` connection, its fire-check callable, and the SFX connection
- `paddle.wall_left_x` / `wall_right_x` assignment (stays `0.0`)
- Creation of `_slow_timer`, `_combo_timer`, `_combo_label`, `_flash_overlay`, `_slow_overlay`

The consequences compound badly:

- **Wall bounds are wrong** — paddle can clip ~20px into the left wall.
- **Laser power-up is dead** — `_paddle` is null in `laser_manager`, so `_fire_laser()` returns immediately every time. The HUD timer runs, nothing fires.
- **Slow Balls becomes permanent** — `_apply_slow_balls()` calls `_slow_timer.start(duration)` on a null Timer, which errors out and aborts the function before the timer (which would later call `_restore_ball_speeds`) is ever armed.
- **Scoring breaks entirely** — `_on_brick_hit()` calls `_combo_timer.start()` on a null Timer as its second line. That errors and aborts the function *before* `score += points + combo_bonus` runs. Every brick hit in Endless Mode silently fails to add score.

There's a second, related issue: in the *normal* (non-endless) branch, `_run_setup()` itself ends with `_start_new_run(current_level)` — and then `_ready()` calls `_start_new_run(current_level)` again right after. That's a redundant double-run-start on every normal launch (double brick spawn, double intro coroutine kickoff). It's currently masked by the `_intro_gen` guard and full teardown in `_load_level()`, so it's not visibly broken — but it's wasteful and fragile, and worth folding into the same fix.
