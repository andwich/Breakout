### MEDIUM — Sticky release clobbers Big Paddle tint

**File:** `entities/paddle.gd` → `_disable_sticky()`

`apply_big_paddle()`/`_reset_paddle_width()` already check `sticky_mode` before touching `sprite.color`, so Big Paddle correctly defers to Sticky's yellow tint. Same pattern as prior multiball/laser intersection bugs — one system's cleanup step didn't check the other's active state.

### LOW — Sticky-catch aim indicator is unreachable

**Files:** `entities/paddle.gd` (`_draw`), `main.gd`

`_draw()` has a branch specifically for showing aim lines while a ball is caught mid-play via Sticky:

```gdscript
var draw_aim := show_aim and (not sticky_mode or (stuck_ball and is_instance_valid(stuck_ball)))
```

But `show_aim` is only ever set `true` in `main.gd::_begin_ready_phase()` and `false` in `_launch_waiting_ball()` — both READY-phase-only. Nothing sets it `true` when `stick_ball()` succeeds during `PLAYING`, so that branch can never actually render. Same category as the old laser-aim issue: a condition written for a case the surrounding code never triggers.

Two ways to close it out — your call:
- **Wire it up:** set `show_aim = true` inside `stick_ball()` and clear it wherever the release actually launches (`_disable_sticky()`'s immediate-launch branch and the deferred-launch block in `_process()`).
- **Remove it:** simplify to `var draw_aim := show_aim` and drop the sticky-specific condition, since it's currently dead.

### LOW — Ball loss only detects bottom-screen exit

**File:** `entities/ball.gd` → `_on_screen_exited()`

```gdscript
func _on_screen_exited() -> void:
	if global_position.y > get_viewport_rect().size.y + 20.0:
		launched = false
		life_lost.emit()
		queue_free()
```

`VisibleOnScreenNotifier2D.screen_exited` fires for *any* exit direction, but only a bottom-exit counts as a loss and gets freed. Under normal play the side/top walls prevent this, but if a ball ever tunnels out (e.g. an unusually fast multiball clone at a steep angle combined with the substep collision loop), it would neither free itself nor count toward `_has_active_ball()` — a permanently "active" phantom ball that can soft-lock the round waiting for a life-loss that never comes, since `screen_exited` only fires once per exit/reentry cycle.

Cheap defensive fix — treat any exit as a loss, not just downward ones:

```gdscript
func _on_screen_exited() -> void:
	launched = false
	life_lost.emit()
	queue_free()
```

## Highest-priority refinement

Centralize paddle appearance instead of having each power-up directly assign `sprite.color`. The current code already recognizes that effects interact—for example, Big Paddle avoids overriding Sticky—but the cleanup path is asymmetric.[1][2]

Use a single derived visual state:

```gdscript
func refresh_visual_state() -> void:
    if sticky_mode:
        sprite.color = GameTheme.NEON_YELLOW
    elif target_width > normal_width:
        sprite.color = GameTheme.NEON_LIME
    else:
        sprite.color = GameTheme.NEON_CYAN
    queue_redraw()
```

Then call it from `apply_big_paddle()`, `reset_paddle_width()`, `enable_sticky()`, `disable_sticky()`, and `reset()`. This eliminates order-dependent behavior as more modifiers are introduced. The project already has a centralized `GameTheme`, so using those named constants would also prevent color drift from inline `Color(...)` values.[1]

## Launch scene and flow

The core sequence is sound: title input transitions through `ScreenTransition`, gameplay initializes level state, displays the level intro, enters `READY`, spawns an attached ball, and accepts Space/click to move into `PLAYING`.[1]

The main launch-scene risks are polish and input handoff rather than correctness:

- **First-click ambiguity:** the title screen starts on `ui_accept` or click, and the new gameplay scene also launches on the same action. Depending on input timing, a click can feel like it skipped part of the onboarding or can launch immediately after the fade. Add a short input-consumption guard in `main.gd`—for example, require the action to be released after scene entry before allowing launch.[1]
- **Ready-state clarity:** the game appears to enter `READY` after a one-second intro, but a stronger “PRESS SPACE / CLICK TO LAUNCH” treatment—pulsing, with the ball/paddle aim lines visually synchronized—would make the first interaction unmistakable. The HUD already has ready-state support and the paddle has aim-line rendering.[1]
- **Brick entrance versus player readiness:** staged brick entrance animation is visually appealing, but the code documentation notes bricks are not interactive until the animation completes. Ensure `READY` does not accept launch until this is complete, or make the animation fast enough that the player never experiences a launched ball passing through a non-interactive board.[1]
- **Transition recovery:** `ScreenTransition` includes a five-second guard and reset API, which is good defensive design. Consider logging a warning when that guard fires; silent recovery makes intermittent launch/scene issues difficult to diagnose.[1]

## Play-mechanic improvements

The game has a solid modern-Breakout foundation: paddle-angle rebounds, sub-stepped ball movement, multiball caps, state-gated laser fire, per-level power-up weighting, and a six-effect power-up set.[1]

I would refine the feel in these areas:

- **Make aiming a coherent mechanic.** The READY aim guide works, but Sticky catching should use the same language: show the guide, let the player steer briefly, then release by the same Space/click action. Alternatively, remove the unused Sticky aim design so the feature remains a quick automatic relaunch rather than a partially signaled precision mechanic.[2][1]
- **Preserve a minimum upward trajectory.** The ball clamps low vertical velocity to avoid long horizontal loops, which is good. Add a post-paddle-hit minimum upward component or maximum shallow rebound angle to reduce frustrating side-to-side “ceiling skating” at higher speeds.[1]
- **Increase multiball readability.** Magenta clones distinguish themselves, but at six balls, laser fire, power-ups, trails, brick particles, and camera shake, the board can become visually saturated. Reduce clone trail alpha/particle count, or reserve the brightest ball treatment for the player’s original ball.[1]
- **Expose brick durability more clearly.** Metal and boss bricks do have HP cues, damage effects, health bars, and shaders. Consider adding a short hit-stop or a stronger crack/flash progression so a player instantly understands whether a collision damaged a tough brick.[1]
- **Test effect intersections as explicit cases.** The tint issue is a signal that effect composition needs regression tests: Sticky + Big Paddle, expiry in both orders, Sticky + Multiball, Sticky expiry during pause, Laser + round clear, Slow + newly spawned multiball, and level transitions with active effects. The project’s own checklist already identifies several of these intersections.[1]

## Aesthetic direction

The neon palette is cohesive: a dark purple-blue background, cyan structural elements, and magenta/lime/yellow/red accents give it a clear retro-arcade identity. Procedural particles, boss glow, metal scanlines, ring effects, screen shake, and synthesized SFX also give the game more personality than a basic Breakout clone.[1]

The main aesthetic risk is **competing emphasis**. The border, paddle, ball trails, bricks, power-ups, HUD, overlays, laser beams, particles, and screen shake all use high-energy neon treatments; at peak action, the player’s visual hierarchy can flatten.[1]

I’d establish a hierarchy:

- **Cyan:** stable structure—border, normal paddle, neutral UI.
- **Brick row colors:** immediate targets and board navigation.
- **Yellow:** actionable, short-lived interaction—launch prompt, Sticky, warnings.
- **Lime:** beneficial status—Big Paddle, positive effects.
- **Magenta/red:** danger, special enemies, high-intensity events.

Use full-screen flashes and strong shake sparingly—boss destruction, life loss, level clear—not on routine pickups or small hits. The present code applies a camera shake and ring effect to every pickup, so reducing the magnitude or varying it by power-up rarity would make marquee moments land harder.[1]
