## Code Review: Breakout

### Bugs & Correctness Issues

**1. Collision layer mismatch (critical)**
In `brick.tscn`, the brick's `collision_layer` is set to `4` (powerup layer) instead of `3` (brick layer). The ball's `collision_mask` is `5` (layers 1+4, i.e. paddle + powerup), which accidentally works, but the laser beam's mask is `5` too — so lasers currently collide on the powerup layer, not the brick layer. This is likely causing silent bugs.

```gdscript
# brick.tscn — should be:
collision_layer = 3  # not 4

# ball.tscn collision_mask = 5 should be:
collision_mask = 7   # paddle (1) + brick (3) = layers 1+2+3 → mask 7 actually... 
# Layer 1=1, Layer 2=2, Layer 3=4, Layer 4=8 — so brick layer 3 = bitmask 4
# This means the current mask=5 (bits 1+4) = paddle + brick — actually correct!
# But laser_beam.tscn collision_mask=5 is also targeting brick correctly.
# The real issue: brick collision_layer=4 means bricks are ON the powerup layer
# → powerups and bricks share layer 4 → paddles detect both on the same channel
```

**2. `_spawn_ball` doesn't call `_connect_new_ball` after `_level_complete`**
In `_level_complete`, you call `_spawn_ball()` then `_connect_new_ball(b)` correctly. But in `_ready`, you call `_spawn_ball()` and separately connect only the first child. If `_spawn_ball` ever adds more than one ball at ready, signals won't be connected. Low risk currently, but fragile.

**3. Sticky ball positioning is relative to local, not global**
In `paddle.gd`, `_stuck_ball.position = position + Vector2(0, -30)` — but `position` here is the paddle's local position. Since paddle is a direct child of Main (not a nested node), this coincidentally works, but `global_position` is the safer choice.

**4. `_on_brick_destroyed` always uses hardcoded `0.25` drop chance**
```gdscript
func _on_brick_destroyed(pos: Vector2):
    if randf() < 0.25:  # ignores b.drop_chance entirely!
```
The brick's `drop_chance` is carefully configured per level in `_configure_brick` but never read here. Boss bricks are supposed to have a higher drop rate (up to 0.6) but always get 0.25.

**Fix:**
```gdscript
# Brick needs to emit its drop_chance in the destroyed signal
signal destroyed(from_position: Vector2, drop_chance: float)
# Or store it and read it in main
```

**5. `HUD.start_powerup_timer` is frame-rate dependent and non-cancellable**
The while loop in `hud.gd` uses `get_process_delta_time()` which returns 0 until the next frame processes — can drift. Also, if two powerups are collected simultaneously, both coroutines run and fight over `powerup_progress`. Use a `Tween` instead.

**6. Ball speed not preserved on velocity bounce**
In `ball.gd`, after bouncing off a wall, `velocity = velocity.bounce(normal)` is fine. But the minimal-velocity fix at the bottom only triggers on `absf(velocity.y) < 50` — balls can still get stuck in nearly-horizontal trajectories since you don't check `velocity.x`.

### Gameplay & Playability Issues

**7. No aim indicator when ball is held**
Players have no visual feedback about *where* the ball will launch. A dotted line or angle indicator from the paddle would significantly improve feel.

**8. Ball launch angle range is too random**
`randf_range(-60, 60)` means balls can shoot almost sideways. A range of `(-45, 45)` or `(-30, 30)` with a bias toward upward angles gives more predictable, playable launches. The `toward` parameter is passed as `Vector2.UP` but immediately discarded — the angle should be relative to `toward`.

```gdscript
# Current (ignores toward direction after rotation):
velocity = toward.rotated(deg_to_rad(angle)) * _speed
# This is actually fine — the rotation IS relative to toward. But the ±60° is too wide.
```

**9. Multiball clones fire at too-similar angles**
```gdscript
clone.velocity = original.velocity.rotated(deg_to_rad(randf_range(20, 40)))
```
Both clones rotate 20–40° in the same direction. One should go negative:
```gdscript
var angles = [-randf_range(25, 45), randf_range(25, 45)]
# spawn two with opposite offsets for natural spread
```

**10. No ball-launch prompt shown on new ball spawn after life loss**
`hud.show_launch_prompt(true)` is never called when a new ball spawns after a life is lost. Players won't know the ball is waiting.

**11. Endless mode level-complete condition is wrong**
```gdscript
if _current_level >= 5:
    get_tree().change_scene_to_file("res://ui/victory.tscn")
```
Once you're in Endless mode (`_current_level > 5`), clearing bricks still triggers `_level_complete()` but this `>= 5` check sends you to the victory screen again! Should be:
```gdscript
if _current_level == 5:
    get_tree().change_scene_to_file("res://ui/victory.tscn")
else:
    _current_level += 1
    # ... spawn next wave
```

**12. Slow ball powerup resets all balls to level speed, not per-ball speed**
After the slow-ball timer expires, all balls are set to `base_speed * speed_mult`. But if the player picked up slow-balls, had a multiball spawn (clones inherit original speed), and then the timer ends — all balls suddenly jump to level speed regardless of their actual speed state.

**13. No score display on game over or level complete**
Players have no way to see their final score when the game ends or compare between levels.

### Architecture & Code Quality

**14. `get_parent().get_parent()` in `ball.gd` is brittle**
```gdscript
@onready var _paddle: Paddle = get_parent().get_parent().get_node("Paddle")
```
This hardcodes scene hierarchy depth. If Ball moves to a different parent level, this silently breaks. Pass the paddle reference via `main.gd` after instantiation, or use a group:
```gdscript
# In main.gd after spawning:
b.set_paddle(paddle)
# or
var _paddle: Paddle = get_tree().get_first_node_in_group("paddle")
```

**15. LaserManager uses `get_parent().get_node("Paddle")` too**
Same fragility. The paddle reference should be injected.

**16. `_brick_count` can go negative**
If a ball and laser hit the same brick simultaneously (or `take_damage` is called twice before `queue_free`), `_on_brick_destroyed` fires once but `_brick_count` was only set for the expected number. The `_already_hit` flag in `LaserBeam` prevents double-counting from lasers, but ball + laser simultaneously isn't guarded. Add:
```gdscript
func _on_brick_destroyed(pos: Vector2):
    _brick_count = max(0, _brick_count - 1)
```

**17. `main.tscn` has a syntax error**
```
script = ExtResource("3_w7kq1"]   # mismatched bracket — [ vs ]
```
This will fail to parse in Godot. Should be:
```
script = ExtResource("3_w7kq1")
```

**18. Ball `_start_pos` captures position at node add time, not paddle position**
In `reset()`, the ball teleports to `_start_pos` which is where the ball was placed in the scene tree — not the paddle's current position. After the paddle moves and a life is lost, the reset ball appears at the original paddle X, not the current X. This is likely intentional for now but worth revisiting.

### Polish / UX Suggestions

**19. No pause functionality** — standard in any arcade game

**20. Power-up stacking not handled** — calling `apply_big_paddle` twice creates two overlapping coroutines that both try to restore the width after their timers, the second one resetting it prematurely

**21. Boss bricks should have a visual HP indicator** — they have `HP_Label` defined but it's hidden for HP ≤ 1; at 5 HP the number shows but disappears too early. Show it until HP = 1, not ≤ 1.

**22. No high score persistence** — `Colors.start_level` is used for state but score resets every game
