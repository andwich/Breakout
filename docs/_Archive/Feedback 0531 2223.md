### 1. Victory transition doesn't halt balls before scene swap `[CRITICAL]`

**File:** `main.gd → _resolve_round_clear()`

**Problem:**
`_resolve_round_clear()` sets `phase = VICTORY` and calls `ScreenTransition.change_scene()` without awaiting it or stopping active balls. If a trailing multiball ball falls through the bottom after the scene swap begins, `_on_ball_lost` fires on the stale `main.gd` node. `_life_lost_pending` may not block this because the deferred `_process_life_loss` can resolve before the scene is fully replaced. This can overwrite `RunState.last_score` after it has already been written, corrupting the value `victory.gd` reads.

**Current code:**
```gdscript
if current_level == LevelDefs.base_levels().size():
    RunState.last_score = score
    phase = GameState.Phase.VICTORY
    _intro_running = false
    ScreenTransition.change_scene("res://ui/victory.tscn")  # not awaited
    return
```

**Fix:**
```gdscript
if current_level == LevelDefs.base_levels().size():
    RunState.last_score = score
    phase = GameState.Phase.VICTORY
    _intro_running = false
    _transitioning = true            # blocks further _on_ball_lost paths
    for b in balls_container.get_children():
        if b is Ball:
            b.set_physics_process(false)
    ScreenTransition.change_scene("res://ui/victory.tscn")
    return
```

> No `await` needed — setting `_transitioning = true` and halting ball physics is enough. The scene swap frees everything else.

### 2. Victory check fires incorrectly if future level count changes `[CRITICAL]`

**File:** `main.gd → _resolve_round_clear()`

**Problem:**
The victory condition is `current_level == LevelDefs.base_levels().size()`. This is semantically wrong: it tests the *current level number* against the *count of base levels*, which happens to equal 5. If you add a 6th authored level later, this condition will never trigger (player clears level 6 → `6 == 6` is fine) — but if the player somehow reaches level 5 mid-endless, it will falsely trigger victory. More immediately: the condition doesn't account for whether this run actually *started* as a story run, meaning an endless mode player who wraps back through level 5 could be incorrectly sent to the victory screen.

**Fix:**
```gdscript
# Clarify intent and guard against endless re-trigger:
var is_last_story_level := (current_level == LevelDefs.base_levels().size()
    and RunState.start_level <= LevelDefs.base_levels().size())
if is_last_story_level:
    RunState.last_score = score
    ...
```

### 3. `ScreenTransition.fade_in()` snapbacks if overlay is already transparent `[HIGH]`

**File:** `screen_transition.gd → fade_in()`, called from `title_screen.gd` and `victory.gd`

**Problem:**
Both `title_screen.gd` and `victory.gd` call `ScreenTransition.fade_in()` unconditionally in `_ready()`. This is correct when the scene was reached via `change_scene()` (overlay is opaque). But when running a scene directly from the Godot editor ("Run This Scene"), the overlay starts transparent. `fade_in()` calls `.from(1.0)`, which instantly snaps the overlay to opaque then tweens it back to transparent — producing a visible black flash on load. Calling it twice (rapid restarts) has the same effect.

**Fix — add a guard in `screen_transition.gd`:**
```gdscript
func fade_in(duration: float = 0.3) -> void:
    _overlay.mouse_filter = Control.MOUSE_FILTER_IGNORE
    if _overlay.color.a < 0.05:   # already transparent, skip
        return
    var tween := create_tween()
    tween.tween_property(_overlay, "color:a", 0.0, duration).from(1.0)
    await tween.finished
```

### 4. Wall boundary offsets hardcode wall thickness as a magic number `[HIGH]`

**File:** `main.gd → _ready()`

**Problem:**
```gdscript
paddle.wall_left_x  = $LeftWall.position.x  + 10.0
paddle.wall_right_x = $RightWall.position.x - 10.0
```
The `±10.0` is the half-width of the wall's `RectangleShape2D` (size = 20). This happens to be correct right now, but it duplicates knowledge of the wall geometry in an unrelated file. If the wall collision shape is ever resized in the `.tscn`, the paddle clamp will silently be wrong without any error.

**Fix — derive from the actual collision shape:**
```gdscript
var left_shape  := $LeftWall/CollisionShape2D.shape  as RectangleShape2D
var right_shape := $RightWall/CollisionShape2D.shape as RectangleShape2D
paddle.wall_left_x  = $LeftWall.position.x  + left_shape.size.x  / 2.0
paddle.wall_right_x = $RightWall.position.x - right_shape.size.x / 2.0
```

### 5. Global powerup drop cooldown penalises multiball `[HIGH]`

**File:** `main.gd → _spawn_powerup()`

**Problem:**
The 0.4 s time-gate on `_last_powerup_drop_time` is global — shared across all balls. During multiball with 4–6 balls destroying bricks simultaneously, the first drop wins the cooldown window and all subsequent drops within 0.4 s are silently discarded. Drop rates collapse exactly when multiball should feel most rewarding. The cooldown was designed to prevent drop floods from single-ball rapid combos, but a per-frame cap achieves the same thing without punishing multiball.

**Current code:**
```gdscript
var now := Time.get_ticks_msec() / 1000.0
if now - _last_powerup_drop_time < 0.4:
    return
_last_powerup_drop_time = now
```

**Fix — replace with a per-frame drop cap:**
```gdscript
# Add as a class variable:
var _drops_this_frame: int = 0

# Reset at the top of _physics_process (or _process):
func _physics_process(_delta: float) -> void:
    _drops_this_frame = 0

# In _spawn_powerup():
func _spawn_powerup(pos: Vector2, drop_chance: float) -> void:
    if randf() >= drop_chance:
        return
    if _drops_this_frame >= 2:      # max 2 simultaneous drops per frame
        return
    _drops_this_frame += 1
    var p := POWERUP_SCENE.instantiate() as PowerUp
    ...
```

> Two simultaneous drops per frame feels generous without flooding the screen. Tune to taste.

### 6. Laser `is_scored()` guard fires after `take_damage()`, allowing double-scoring `[MEDIUM]`

**File:** `laser_manager.gd → _fire_laser()` body_entered callback

**Problem:**
The callback structure is:
```gdscript
body.take_damage(1)
if body.is_scored():
    return
```
`take_damage()` calls `destroy()` which sets `_scored = true`. By the time `is_scored()` is checked, it's already true — and the return skips the scoring emit entirely. But if a ball hit the same brick in the same physics frame (before the laser), `_scored` is already true *before* `take_damage()` runs, and the laser still deals damage to an already-destroyed brick. Moving the guard before `take_damage()` fixes both cases.

**Fix:**
```gdscript
laser.body_entered.connect(func(body):
    if body is Brick:
        if body.is_scored():        # guard BEFORE take_damage
            laser.queue_free()
            return
        body.take_damage(1)
        if body.is_queued_for_deletion():
            brick_scored.emit(body.point_value)
        else:
            brick_scored.emit(5)
    laser.queue_free()
, CONNECT_ONE_SHOT)
```

### 7. Sticky and big-paddle timers run while paused `[MEDIUM]`

**File:** `paddle.gd → _ready()`

**Problem:**
`_sticky_timer` and `_big_paddle_timer` don't set a `process_mode`, so they inherit `INHERIT` from Paddle — which means they keep ticking while `get_tree().paused = true`. When `_sticky_timer` expires mid-pause, `_disable_sticky()` correctly skips launching the ball (it checks `get_tree().paused`), but it still sets `stuck_ball = null`. When the player unpauses, the ball is no longer stuck and hasn't been launched — the sticky state is silently lost. Same issue for big paddle: the upgrade duration drains during pause.

**Fix:**
```gdscript
func _ready() -> void:
    _big_paddle_timer = Timer.new()
    _big_paddle_timer.one_shot = true
    _big_paddle_timer.process_mode = Node.PROCESS_MODE_PAUSABLE  # add this
    _big_paddle_timer.timeout.connect(_reset_paddle_width)
    add_child(_big_paddle_timer)

    _sticky_timer = Timer.new()
    _sticky_timer.one_shot = true
    _sticky_timer.process_mode = Node.PROCESS_MODE_PAUSABLE      # add this
    _sticky_timer.timeout.connect(_disable_sticky)
    add_child(_sticky_timer)
```

### 8. Ball bounce branch double-normalises velocity `[MEDIUM]`

**File:** `ball.gd → _physics_process()`

**Problem:**
In the wall/brick bounce branch:
```gdscript
velocity = velocity.bounce(normal)
velocity = velocity.normalized() * speed   # first normalise
_clamp_min_speed()                         # second normalise (redundant)
```
`_clamp_min_speed()` already ends with `velocity = velocity.normalized() * speed`, so the line before it is a redundant no-op. It's harmless but confusing — it implies the caller is responsible for normalisation, when `_clamp_min_speed()` is designed to own that.

**Fix — remove the redundant line:**
```gdscript
velocity = velocity.bounce(normal)
# Remove: velocity = velocity.normalized() * speed
_clamp_min_speed()
```

### 11. Boss brick damage flash can restore wrong color mid-glow tween `[LOW]`

**File:** `brick.gd → take_damage()`

**Problem:**
On damage, boss bricks tween `_sprite.color` to white then call `_update_visual()` to restore it. `_update_visual()` computes `dimmed = row_color.darkened(...)` based on current HP. If the looping `glow_intensity` tween changes the visual state between the white flash and the restore callback, the restored color may be one frame behind. The result is a brief wrong-shade flicker on the boss brick after each hit.

**Fix — save the target color before tweening:**
```gdscript
# In take_damage(), for boss bricks:
if brick_type == "boss":
    var hp_ratio := float(_hp) / float(max_hp)
    var target_color := row_color.darkened(1.0 - clampf(hp_ratio, 0.3, 1.0))
    var tw := create_tween()
    tw.tween_property(_sprite, "color", Color.WHITE, 0.04)
    tw.tween_property(_sprite, "color", target_color, 0.07)
    # Don't call _update_visual() in the tween callback
```

The only indication that sticky mode is active is the yellow `sprite.color` tint. The aim V-lines only appear when a ball is caught. ### 13. HUD effect bar doesn't reset its modulate color when cleared early `[LOW]`

**File:** `hud.gd → clear_effect_timer()`

**Problem:**
`set_effect_timer()` runs an amber warning tween at 2 s remaining, which changes `row.bar.modulate` to `Color(1.0, 0.7, 0.1)`. If the effect is cleared early (e.g. slow balls removed by level transition), `clear_effect_timer()` hides the row and kills the tweens — but doesn't reset `row.bar.modulate`. Effect row objects are reused via `_effect_rows`, so the next effect to reuse that row will start with an amber bar instead of its proper tint color, and remain amber until it happens to trigger its own warning tween.

**Fix — reset modulate before hiding:**
```gdscript
func clear_effect_timer(effect_id: String) -> void:
    if not _effect_rows.has(effect_id):
        return
    var row = _effect_rows[effect_id]
    row.bar.modulate = Color.WHITE   # reset before hiding
    row.root.visible = false
    row.bar.value = 0.0
    if _effect_tweens.has(effect_id):
        for t: Tween in _effect_tweens[effect_id]:
            if t and t.is_valid():
                t.kill()
        _effect_tweens.erase(effect_id)
```
