# Code Review: Breakout

This is a well-architected Godot 4.7 project — clean separation (autoloads, entities, game logic, UI), a disciplined signal/Callable pattern, and thoughtful touches like adaptive ball substeps and per-frame effect rate-limiting. The recent "calm dashboard" retheme is thorough. Below are refinements focused on **playability** and **aesthetics**, ordered by impact.[1][2][3]

## Playability

### Ball paddle-bounce is too forgiving at the edges

In `ball.gd`, the rebound math clamps `hit_ratio` to ±1.0 then maps it to `Vector2(hit_ratio * 0.82, -1.0)`.  The `0.82` horizontal bias means even a dead-center edge hit produces a max angle of `atan(0.82) ≈ 39°` from vertical. Combined with the `aim.y = minf(aim.y, -0.38)` floor, the ball can never be sent truly steep — so reaching bricks tucked in the top corners behind walls is harder than it should be, and long shallow rallies are only partially prevented. Consider widening the max deflection to `0.95`–`1.0` and raising the upward floor slightly so skilled edge-hits are rewarded with sharper angles.[4]

### Stuck-ball escape can fire the ball downward into a loss

When the ball hasn't moved for 30 frames, the escape nudge uses `_last_velocity.normalized()` rotated ±40°, or a random `Vector2(randf_range(-0.5, 0.5), -1.0)` fallback.  If `_last_velocity` was pointing *down* (e.g., ball wedged after a downward bounce), the escape vector keeps that downward sign and can push the ball straight past the paddle into a life loss — punishing the player for a physics glitch. Force the escape direction's `y` to be negative (upward) before applying speed.[4]

### Combo window is invisible to the player

The combo timer resets after `0.6s` and combos ≥3 award bonus points, but there's no UI affordance showing the window closing.  The `_combo_label` only appears at combo ≥3 and fades on its own schedule. A thin decaying progress bar (or the label draining alpha over the actual 0.6s window) would make the mechanic legible and encourage aggressive play — right now players don't know why a combo dropped.[5]

### Mouse control fights keyboard control

In `paddle.gd._physics_process`, keyboard input is only honored when `direction != 0.0`; the moment the key is released, the paddle snaps back to tracking the mouse cursor.  If the player's cursor is resting anywhere off-center, releasing `A`/`D` causes an unintended drift. Track "last input source" and only follow the mouse once the mouse has actually moved since the last keypress.[6]

### Multiball cap silently wastes the power-up

`MAX_BALLS := 6` and each active ball spawns 2 clones, but if you're already at 5 balls the power-up yields almost nothing while still consuming the drop.  Consider spawning at least one clone regardless, or converting an over-cap pickup into bonus points so it never feels like a dud.[7]

## Aesthetics

### Font is bundled but never applied

`Mono-Bold.tres` exists and `project.godot` sets `default_font` — but the retro notes flag it as "not yet wired into any scene/theme," and several HUD labels hardcode `font_size` overrides that will render in the engine default regardless.  Verify the `[font] default_font` actually resolves; if labels still fall back, add a shared `Theme` resource and assign it to the HUD/title/victory roots so typography is consistent.[3][8]

### Brick row colors fight the "calm" palette

`level_builder.gd`'s `ROW_COLORS` uses 8 highly saturated neons (`#12E8FF`, `#39FF63`, `#FF2D1A`…).  But `_update_visual()` in `brick.gd` *overrides* standard bricks to a single `BRICK_STANDARD.darkened(0.12)` tint — so the per-row banding you compute is discarded for the most common brick type.  Either apply `row_color` to the sprite (restoring the intended rainbow-band look) or drop `ROW_COLORS` to the 2–3 muted tones that match the new dashboard aesthetic. Right now the two systems are dead code relative to each other.[9][10]

### Damage flash uses pure white, breaking the muted grade

Both `brick.gd` and the boss path flash `Color(1,1,1)` / `Color.WHITE` on hit.  Against a near-black, desaturated field, a full-white 0.04s flash reads as harsh. Tint the flash toward the brick's own hue lightened (e.g., `base_color.lightened(0.7)`) to keep impact feedback within the calm grade.[9]

### Background scanline + particles may be too subtle to register

The retheme dropped the background scanline to `intensity 0.08` / `speed 0.5` and particle alpha to `0.08`.  On many displays that's effectively invisible, leaving a flat near-black field. A barely-perceptible vignette or a very slow gradient drift would add depth without breaking the calm feel — worth an in-engine look as the retro suggests.[11][3][7]

## Code Health

- **Dead constant**: `Ball.MAX_STEP_DISTANCE`/`MAX_PHYSICS_STEPS` are documented in the readme as the substep system, which is good — but the "residual move" path after the step loop (`if remaining > 0.01 and collision == null`) can tunnel on severe hitches; it's a reasonable tradeoff, just note it.[2][4]
- **`_glow_tween` declared but never used** in `main.gd` — remove or wire it.[1]
- **Duplicated tween-kill guards**: the `if tween and tween.is_valid(): tween.kill()` pattern repeats ~10× across `main.gd`/`brick.gd`/`hud.gd`. A tiny `TweenHelper.kill_if_valid(t)` utility would shrink this.
- **`game_theme.gd` aliases**: the `NEON_*` compatibility aliases are marked "remove after migration" — the migration is done, so these can be deleted to prevent regressions.[12]

The single highest-leverage change for *feel* is the paddle-bounce angle widening; for *polish*, wiring the bundled font into a shared theme.

## P1 — Widen paddle-bounce angle (highest playability leverage)

**Why:** `hit_ratio * 0.82` caps the launch angle at ~39° from vertical, so corner bricks are unreachable and edge skill isn't rewarded.[4]

`entities/ball.gd` — line 155:
```diff
-		var aim := Vector2(hit_ratio * 0.82, -1.0).normalized()
-		aim.y = minf(aim.y, -0.38)
+		var aim := Vector2(hit_ratio * 1.0, -1.0).normalized()
+		aim.y = minf(aim.y, -0.42)
 		aim = aim.normalized()
```
`1.0` lets a full edge hit reach ~45°; raising the floor to `-0.42` keeps the shallowest return from stalling into wall rallies. **Verify:** catch the ball on the paddle's outer edge — it should now leave at a visibly steeper angle than before.

## P2 — Stuck-ball escape must fire upward

**Why:** the escape vector reuses `_last_velocity`, which can point *down*, shoving a wedged ball past the paddle into an undeserved life loss.[4]

`entities/ball.gd` — lines 97–98:
```diff
-			var escape_dir := _last_velocity.normalized() if _last_velocity.length_squared() > 0.01 else Vector2(randf_range(-0.5, 0.5), -1.0).normalized()
-			velocity = escape_dir.rotated(deg_to_rad(randf_range(-40, 40))) * speed
+			var escape_dir := _last_velocity.normalized() if _last_velocity.length_squared() > 0.01 else Vector2(randf_range(-0.5, 0.5), -1.0).normalized()
```

Forces the escape upward with a minimum vertical component so the nudge always travels toward the bricks. **Verify:** hard to trigger on demand; trust the sign logic and the headless gate.
