Breakout codebase review — launch, mechanics, and aesthetic findings

Launch & scene management

4 findings
High _on_ball_lost not guarded against LEVEL_INTRO phase
main.gd

The guard only skips GAME_OVER and ROUND_CLEAR. During the 1.2-second LEVEL_INTRO await, no ball exists yet — but if one survived from a prior round somehow (e.g. a sticky-caught ball during a rapid transition) and exits the screen, a life is incorrectly deducted.

func _on_ball_lost() -> void:
    if phase in [GameState.Phase.GAME_OVER, GameState.Phase.ROUND_CLEAR]:
        return   # LEVEL_INTRO missing from this guard
Fix
if phase in [GameState.Phase.GAME_OVER, GameState.Phase.ROUND_CLEAR,
             GameState.Phase.LEVEL_INTRO]:
    return
Medium Initial phase value is misleading
main.gd

phase starts as TITLE but _ready() immediately calls _start_new_run() → _load_level() → _start_level_intro(), which sets it to LEVEL_INTRO. During the gap before _start_level_intro runs, input handling reads a stale TITLE value that main.gd never actually uses. An input arriving in this window (unlikely but possible on fast machines) could match no branch and silently no-op.

Fix
var phase: GameState.Phase = GameState.Phase.LEVEL_INTRO
Low Redundant RunState reset in title screen
ui/title_screen.gd

RunState.reset() already sets start_level = 1, making the next line a no-op. Minor but confusing if someone changes reset() in the future.

func _start_game() -> void:
    RunState.reset()
    RunState.start_level = 1  # redundant — reset() already does this
Fix — remove the second line
func _start_game() -> void:
    RunState.reset()
    get_tree().change_scene_to_file("res://main.tscn")
Low Pause toggle restores incorrect phase when unpausing with a waiting ball
main.gd

Unpausing correctly determines READY vs PLAYING, but show_aim isn't re-set when unpausing into READY. The aim indicator stays hidden if the player paused mid-READY phase.

Fix
get_tree().paused = false
if _get_waiting_ball() != null:
    phase = GameState.Phase.READY
    paddle.show_aim = true      # restore aim lines
else:
    phase = GameState.Phase.PLAYING
hud.show_pause(false)

Play mechanics

5 findings
High Double-coloring standard bricks: modulate and sprite.color both set to row_color
game/level_builder.gdentities/brick.gd

In level_builder.gd, brick.modulate = ROW_COLORS[row] is set, and then _update_visual() in brick.gd also sets _sprite.color = row_color. Godot multiplies these: a cyan sprite (R=0.2, G=1.0, B=1.0) under a cyan modulate renders as (0.04, 1.0, 1.0) — a washed-out, over-saturated teal. Neon colors lose their intended hue.

# level_builder.gd — line ~50
if brick_type == "standard":
    brick.modulate = ROW_COLORS[row]   # sets whole node modulate
# then brick.gd _update_visual() runs:
_sprite.color = row_color              # also sets the sprite — they compound!
Fix — remove the modulate assignment from level_builder; brick.gd owns coloring
# level_builder.gd — just set row_color export, nothing else
brick.row_color = ROW_COLORS[row]
# remove: brick.modulate = ROW_COLORS[row]
Medium Standard brick alpha fade is dead code
entities/brick.gd

The alpha fade in _update_visual() only fires for brick_type == "standard". Standard bricks have 1 HP, so max_hp - _hp is always 0 until the brick is destroyed (at which point it's freed). The visual never shows. Meanwhile, metal and boss bricks (where this could look great) are handled by their own match branches which skip this code entirely.

if brick_type == "standard":
    var alpha := 1.0 - float(max_hp - _hp) / max_hp * 0.4
    modulate.a = alpha   # fires, but _hp is always max_hp for 1-HP bricks
Fix — move fade to metal/boss, or add multi-HP standard bricks; as-is, remove or guard it
# For metal bricks, add in their match branch:
"metal":
    ...
    var alpha := 1.0 - float(max_hp - _hp) / float(max_hp) * 0.45
    modulate.a = clampf(alpha, 0.55, 1.0)
Medium Powerup drop cooldown blocks all drops globally, even on distinct bricks
main.gd

The 2-second global cooldown in _spawn_powerup prevents drops from any brick within that window. When a multiball chain destroys several bricks in quick succession, players are effectively penalized for being good — the extra balls that earned those kills get no reward. The cooldown's intent (prevent drop spam on one destruction event) is right, but the scope is too wide.

if now - _last_powerup_drop_time < 2.0:
    return   # blocks ALL drops for 2 seconds globally
Option — tighten the window or replace with a probabilistic dampen
# Reduce to 0.8s so multiball chains can still reward players across a fight
if now - _last_powerup_drop_time < 0.8:
    return
Medium Wall boundary doesn't align with paddle movement clamp
main.tscnentities/paddle.gd

Left wall is a 20px body centered at x=10 (inner edge at x=20). Right wall centered at x=1270 (inner edge at x=1260). The paddle is clamped from target_width/2 (50px) to 1280 - 50 = 1230px. So the paddle's left edge can reach x=0 — inside the left wall collision shape. The ball bounces off the wall at ~x=28 but the paddle sprite can visually overlap the wall.

Fix — align wall inner edges with paddle clamp edges
# Paddle clamp uses target_width/2 as margin, so walls should sit at:
position.x = clamp(position.x, target_width / 2.0 + 10.0,
                   limit - target_width / 2.0 - 10.0)
# Or move LeftWall to x=60, RightWall to x=1220 to match the 50px paddle half-width
Low Sticky mode: no visual feedback on paddle color change
entities/paddle.gd

When sticky activates, only the aim-indicator V-lines change. The paddle sprite remains the same cyan. Players have no obvious cue that sticky is active until a ball actually sticks. The HUD timer strip helps, but an in-world signal (color shift, pulse) would make the mode state legible at a glance.

Suggested addition to enable_sticky and _disable_sticky
func enable_sticky(duration_sec: float = 8.0) -> void:
    sticky_mode = true
    sprite.color = Color(1.0, 1.0, 0.4)   # yellow tint = sticky signal
    _sticky_timer.start(duration_sec)
    queue_redraw()

func _disable_sticky() -> void:
    sticky_mode = false
    sprite.color = Color(0.2, 1.0, 1.0)   # restore cyan
    ...

Aesthetics

4 findings
Medium Particle process materials duplicated per brick at build time, not per-instance
game/level_builder.gd

mat.duplicate() is called inside the brick-build loop, so every brick gets its own material copy. This is correct but also happens in brick.gd _update_visual() for boss/metal bricks where the material is already cached. The paths converge inconsistently: level_builder sets particle colors via a fresh duplicate, while brick.gd sets _sprite.color through a different branch. Metal/boss particle colors are set in _update_visual only, which means level_builder's duplicate call for those types creates materials that are immediately overwritten. Clean this up so level_builder only sets row_color and brick.gd handles all visual state in one place.

Fix — remove particle material work from level_builder entirely
# level_builder.gd — delete the particle block:
# var particles := brick.get_node("Particles") as GPUParticles2D
# if particles:
#     var mat := ...
#     mat = mat.duplicate()
#     particles.process_material = mat
# brick.gd _ready() already handles this via row_color
Medium Power-up capsules are visually flat — no drift or rotation during fall
entities/powerup.gd

Power-ups fall straight down with only an alpha pulse. A slight horizontal sine-wave drift and slow rotation would make them feel like physical objects and be more immediately legible as collectibles against the static brick field. The alpha pulse alone reads as a UI flicker rather than a "pick me up" invitation.

Suggested addition to _physics_process
func _physics_process(delta: float) -> void: position.y += fall_speed * delta # gentle sine-wave horizontal drift position.x += sin(Time.get_ticks_msec() * 0.003) * 0.8 rotation += delta * 1.2 # slow rotation, ~69°/sec if position.y > get_viewport_rect().size.y + 50: queue_free()
Medium Boss bricks: glow shader center-point conflicts with pulsing scale animation
entities/brick.gdshaders/brick_glow.gdshader

The scale pulse tween (1.0→1.08→1.0) stretches the brick node but the glow shader computes edge from UV coordinates, which stay fixed. As the brick scales up, the glow "moves" inward relative to the physical edge — the center-bright effect becomes inconsistent with the visible border. At 1.08× scale with a 24px tall brick, the mismatch is small but creates a shimmer artifact on the outermost pixels during the pulse peak.

Option A — animate shader glow_intensity instead of node scale
if is_boss:
    var tween := create_tween().set_loops()
    tween.tween_method(
        func(v): _shader_mat.set_shader_parameter("glow_intensity", v),
        1.5, 3.0, 0.6)
    tween.tween_method(
        func(v): _shader_mat.set_shader_parameter("glow_intensity", v),
        3.0, 1.5, 0.6)
Low HUD effect timer bars have no minimum visible fill as they approach zero
ui/hud.gd

The ProgressBar tween goes from duration_sec to 0.0 linearly, meaning the bar silently disappears when empty. A short "final flash" or color-shift in the last second (e.g. bar turns red/amber) would give the player a clear warning before the effect ends rather than a sudden vanish. The current clear-on-complete callback also removes the row immediately with no exit animation.

Suggested — pulse bar color when <2s remain
func set_effect_timer(...) -> void: ... var new_tween := create_tween() new_tween.tween_property(row.bar, "value", 0.0, duration_sec) # when 2s remain, shift bar to warning amber if duration_sec > 2.0: new_tween.parallel().tween_interval(duration_sec - 2.0) new_tween.tween_property(row.bar, "modulate", Color(1.0, 0.7, 0.1), 0.3) new_tween.tween_callback(func(): clear_effect_timer(effect_id))
