Breakout code review — 9 issues across play mechanics, scene launch, and aesthetics

Play mechanisms

1

_on_ball_lost can trigger _enter_game_over multiple times

If two balls exit the bottom in the same frame, both fire life_lost. _has_active_ball() returns false for each before either processes, so lives is decremented twice and _enter_game_over is called twice. max(0, lives - 1) prevents negative lives but doesn't guard the double game-over call. Add a guard: if phase == GameState.Phase.GAME_OVER: return at the top of _on_ball_lost.

main.gd _on_ball_lost()

Critical
2

Paddle size and sticky state persist across levels

_load_level() resets position and re-enables processing, but _big_paddle_timer and _sticky_timer keep running from the previous round. When they fire on the new level, _reset_paddle_width() and _disable_sticky() run against stale state. Call paddle._reset_paddle_width() and paddle.stuck_ball = null; paddle.sticky_mode = false (plus stop both timers) at the start of _load_level, or add a reset() method to Paddle.

main.gd _load_level() · entities/paddle.gd

Critical
3

Ball hit on lethal brick double-counts score

When a ball kills a 1-HP brick in a single hit, brick_hit.emit(1) fires first (1 pt), then brick_hit.emit(collider.point_value) fires immediately after because is_queued_for_deletion() is already true. For a standard row-5 brick worth 10 pts, the player gets 11 instead of 10. On higher-HP bricks the two emissions are intentional (per-hit 1 pt + death bonus), but on 1-HP bricks the 1-pt per-hit emission is redundant. Gate the per-hit emit on not collider.is_queued_for_deletion().

entities/ball.gd _physics_process (brick branch)

Significant
4

score_sfx.play() with no stream assigned generates errors on every hit

ScoreSfx is an AudioStreamPlayer with no stream set in the scene. Calling play() on it emits a Godot error every brick hit, including the constant per-hit 1-pt awards from laser + metal bricks. Guard with if score_sfx.stream: score_sfx.play(), or remove the call until audio assets exist.

main.gd _on_brick_hit() · main.tscn ScoreSfx

Significant
5

_clamp_min_speed is called after paddle hits but its normalization can still shrink velocity

The paddle-hit path sets velocity from aim * velocity.length() then calls _clamp_min_speed(). Inside, after clamping components it calls velocity.normalized() * max(cur_speed, 50.0) — if the incoming speed was already below 50 px/s this is fine, but if velocity.length() was, say, 30, the normalise step sets a direction and the clamp re-scales to 50. The real issue is that _clamp_min_speed is now only called from the paddle path; the bounce path has its own inline version without the final normalise. The standalone function's final normalise is harmless but inconsistent with the inline version and could mask edge cases. Unify both paths to use the same logic.

entities/ball.gd _clamp_min_speed() vs inline bounce clamp

Minor

Launch / scene

6

_start_level_intro await is unguarded against scene changes

If _start_level_intro() is called and get_tree().change_scene_to_file() fires before its 1.2s timer resolves (e.g. a stale _on_brick_destroyed signal after _load_level clears bricks and fires the signal in the same frame), the resumed coroutine calls hud.hide_level_intro() and _begin_ready_phase() on a partially-freed scene tree. Check is_inside_tree() after each await in both _start_level_intro and _resolve_round_clear before continuing.

main.gd _start_level_intro(), _resolve_round_clear()

Significant
7

brick.tscn collision_layer is 4 (bitmask) but layer named "powerup" is also 4

In project.godot, layer_names/4="powerup" is bit 4 = bitmask value 8, not 4. The bitmask value 4 is bit 3, named "brick". So collision_layer = 4 in brick.tscn is correct — bricks are on the brick layer. However powerup.tscn uses collision_layer = 8 correctly (bit 4). This notation is correct but confusing given that the layer number and its bitmask value are different. Worth a comment in both tscn files to prevent future editors from "fixing" them wrongly.

entities/brick.tscn, entities/powerup.tscn, project.godot

Minor

Aesthetic

8

LevelIntroPanel has no background — renders transparent over gameplay

LevelIntroPanel is a PanelContainer but the HUD tscn applies no theme or StyleBox to it, so in Godot 4 it defaults to the engine's flat dark theme — or transparent if no default theme is loaded. The text will render directly over mid-game bricks and particles, making it unreadable. Add a StyleBoxFlat with a semi-opaque fill (e.g. Color(0.08, 0.05, 0.15, 0.88) matching GameTheme.NEON_BG) and 1px cyan border, or replace with a ColorRect + VBoxContainer.

ui/hud.tscn LevelIntroPanel

Critical
9

Victory screen HighScoreLabel has no explicit hide in _ready — relies solely on tscn default

victory.gd _ready() only sets high_score_label.visible = true when a score exists, but never sets it false. If the tscn node default ever changes or the scene is reused, first-run players would see an empty label taking up layout space. A one-liner guard at the top of _ready() makes the intent explicit and immune to tscn changes: high_score_label.visible = false.

ui/victory.gd _ready() · ui/victory.tscn HighScoreLabel

Minor
