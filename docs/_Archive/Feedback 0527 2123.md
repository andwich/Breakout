## Launch / Scene Management

**1. `_start_level_intro` has an orphaned await after scene change**

In `main.gd`, `_resolve_round_clear()` calls `_load_level(current_level + 1)` which calls `_start_level_intro()`. But if the player is on Level 5 and the round clears, `ScreenTransition.change_scene()` fires and the scene is torn down — yet `_start_level_intro` has an `await get_tree().create_timer(1.0).timeout` that's now dangling. You have `if not is_inside_tree(): return` as a guard after the await, which catches this *most* of the time, but there's a race: if the fade starts before the 1-second timer fires, the node may still be in the tree briefly. The `_intro_running` flag helps but isn't sufficient on its own because `_resolve_round_clear` doesn't set it false before changing scenes. 

Fix: set `_intro_running = false` at the top of `_resolve_round_clear` before calling `ScreenTransition.change_scene()`.

**2. `ScreenTransition._busy` is never reset on scene change failure**

In `screen_transition.gd`, if `change_scene()` is called and something goes wrong mid-transition (e.g., the path is bad), `_busy` stays `true` permanently — the game is silently stuck with no way to recover. A try/catch or reset on error would help, and at minimum the `fade_in` should run even if the scene change errors.

**3. Title and victory screens don't stop their tweens on scene exit**

Both `title_screen.gd` and `victory.gd` create looping tweens (the prompt pulse, the title glow, the confetti timer) that are never explicitly stopped. In Godot 4, looping tweens created with `create_tween()` do stop when the node is freed — but the `_confetti_timer` in `victory.gd` is a `Timer` node added as a child, which keeps spawning `ColorRect` pieces. If `start_endless()` triggers quickly (the player hammering confirm), you can end up with orphaned confetti rects in the scene tree during the fade transition since they're children of the victory control, and the transition fade may reveal them over the new scene momentarily. Stopping `_confetti_timer` at the top of `start_endless()` and `_unhandled_input` (before the scene change) would fix this.

## Play Mechanisms

**4. Ball scoring emits on destroyed bricks even when the ball itself caused the destroy**

In `ball.gd`'s collision handler:
```gdscript
if collider is Brick:
    collider.take_damage(1)
    if not collider.is_queued_for_deletion():
        brick_hit.emit(1)
    else:
        brick_hit.emit(collider.point_value)
```
But `take_damage()` calls `destroy()` which calls `destroyed.emit()`, and `_on_brick_destroyed` in `main.gd` handles the brick destruction side. The ball also emits `brick_hit` with `point_value` on the same frame. Meanwhile `_on_brick_hit` in `main.gd` adds to score. So far so good. The issue is: laser hits also call `brick_scored.emit` (connected to `_on_brick_hit`), and if a laser and ball hit the same brick in the same frame, you can get double scoring — `take_damage` from the laser fires first (inside the `body_entered` lambda), then the ball's collision resolves and the brick is already `queued_for_deletion`, so the ball emits `point_value` again. This is an inherent race in single-frame multi-source damage. Mitigating it: track a `_scored` flag on `Brick` that gets set in `destroy()`, and only emit score once.

**5. `_has_active_ball()` check in `_on_ball_lost` can mask a real life loss with multiball**

The logic:
```gdscript
func _on_ball_lost() -> void:
    if phase in [...]:
        return
    if _has_active_ball():
        return   # ← correct, other balls still in play
    if _life_lost_pending:
        return
    _life_lost_pending = true
    call_deferred("_process_life_loss")
```

This is correct for the happy path. But consider: two balls exit the bottom on the same frame. Both pass the `_has_active_ball()` check (neither is "launched" by the time the second one checks, since `life_lost.emit()` triggers `queue_free` in `ball.gd` before `launched` is cleared). Both set `_life_lost_pending` — but the second one is blocked by the flag. ✓ That part's fine. However, `_on_ball_lost` in `ball.gd` sets `launched = false` *then* emits `life_lost`, so for the very brief window between those two lines on ball A, `_has_active_ball()` would return false for ball B that's still in motion. This is very unlikely to actually matter in practice but is worth noting if you ever see phantom double life losses.

**6. Slow ball restoration doesn't account for big paddle overlap timing**

When `_restore_ball_speeds` fires, it sets `b.speed = b.base_speed * speed_mult`. But `_apply_slow_balls` stores no reference to the pre-slow speed — it just applies `* _slow_factor`. If slow expires while playing a level where `speed_mult` has changed mid-session (impossible currently since you always load a new level), or if endless mode scaling changes, the restore would be correct because it reads `config_for_level` fresh. This is actually fine as-is. However: there's no HUD `clear_effect_timer` call on the slow timer in `_restore_ball_speeds`. If the slow expires naturally via `_slow_timer.timeout`, the HUD bar clears itself via the tween callback in `set_effect_timer`. But if `_restore_ball_speeds` is called early (e.g. from `_start_new_run`), the HUD timer keeps ticking visually even though speed is restored. 

Fix: call `hud.clear_effect_timer(PowerUpRegistry.effect_id_for(PowerUp.Type.SLOW_BALLS))` at the top of `_restore_ball_speeds`.

**7. Powerup collected during `ROUND_CLEAR` is blocked, but it's still `queue_free`'d**

```gdscript
func _on_powerup_collected(ptype, duration) -> void:
    if phase != GameState.Phase.PLAYING:
        return
    ...
```

The `return` is correct — you don't apply the effect. But the powerup itself already called `queue_free()` in its own `_on_body_entered` *before* emitting `collected`. So the powerup disappears and the effect is silently discarded, which is the right behavior. This is fine — just confirming it's intentional and working.

## Aesthetic

**8. `_combo_label` position calculation uses `get_minimum_size()` but the label hasn't been laid out yet on first call**

```gdscript
_combo_label.position = Vector2(
    (get_viewport_rect().size.x - _combo_label.get_minimum_size().x) / 2.0,
    ...
)
```

`get_minimum_size()` on a Label that hasn't been through a layout pass returns `Vector2.ZERO`, so the first combo display will be left-aligned instead of centered. Subsequent calls after the first layout pass will be correct. The fix is to call `_combo_label.reset_minimum_size()` before reading it, or defer the position update with `call_deferred`.

**9. Ball glow layers are multiplicative with `ball_color` but the outer halo uses full white**

```gdscript
draw_circle(Vector2.ZERO, 14.0, Color(1.0, 1.0, 1.0, 0.12) * ball_color)
draw_circle(Vector2.ZERO, 10.0, Color(1.0, 1.0, 1.0, 0.25) * ball_color)
draw_circle(Vector2.ZERO, 8.0, ball_color)
```

Multiplying `Color(1,1,1,0.12)` by `ball_color` just gives `ball_color` at 12% alpha, which is correct and intentional. However for the magenta multiball clones (`NEON_MAGENTA = Color(1.0, 0.2, 0.8)`), the middle ring at 0.25 alpha will look quite washed out because the green channel is 0.2. This is a minor aesthetic quibble but you could give clone balls a slightly larger base radius or stronger alpha to compensate for the darker hue.

**10. `_animate_brick_entrance` stagger timing vs. intro panel hide timing**

`_start_level_intro` shows the panel, awaits 1.0s, hides it, then calls `_begin_ready_phase`. But `_animate_brick_entrance` is called from `_load_level` *before* `_start_level_intro` — so all bricks complete their entrance animation (1 second of delay + animation ≈ `0.015 * brick_count + 0.2`) while the intro panel is still visible. For Level 5 with 84 bricks that's about 1.46 seconds. The bricks finish animating, then the panel hides. This is fine visually — bricks settle behind the panel — but if you wanted the brick entrance to coincide with the panel *hiding*, you'd move `_animate_brick_entrance` to `_begin_ready_phase`. Worth considering as a deliberate design choice.

**11. Screen shake on multiple simultaneous brick destructions stacks via multiple tweens**

`_shake_camera` creates a new tween each call, and each tween resets `position` to `orig` at the end. If 3 bricks are destroyed in one frame (e.g. multiball cluster), you get 3 independent tweens all competing to move `position` around. The last one to finish snaps position to *its* captured `orig`, which may be offset from the actual resting position if another tween moved it in between. The result is a visible position jump after multi-brick destruction.

Fix: track a `_shake_tween` variable, kill it before starting a new one, and accumulate intensity instead:
```gdscript
var _shake_intensity: float = 0.0
var _shake_tween: Tween

func _shake_camera(intensity: float, duration: float) -> void:
    _shake_intensity = minf(_shake_intensity + intensity, 8.0)
    if _shake_tween and _shake_tween.is_valid():
        return  # let current tween finish, intensity already added
    var orig := position
    _shake_tween = create_tween()
    _shake_tween.tween_method(func(t):
        var decay := 1.0 - t
        position = orig + Vector2(randf_range(-_shake_intensity, _shake_intensity), randf_range(-_shake_intensity, _shake_intensity)) * decay
    , 0.0, 1.0, duration)
    _shake_tween.tween_callback(func(): position = orig; _shake_intensity = 0.0)
```
