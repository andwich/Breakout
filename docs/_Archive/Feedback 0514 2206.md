## 🔴 Launch / Scene Flow Issues

### 1. `_start_level_intro()` has a dangling await
In `main.gd`, `_start_level_intro()` does:
```gdscript
await get_tree().create_timer(1.2).timeout
if not is_inside_tree():
    return
hud.hide_level_intro()
_begin_ready_phase()
```
If the player dies during a level and `_load_level()` is called while the timer from the *previous* `_start_level_intro()` is still running, both timers will resolve and `_begin_ready_phase()` can be called twice — spawning two balls. **Fix**: Store the timer and cancel it on `_load_level()`, or use a sequence flag (`_intro_running`).

### 2. Wall collision layers are invisible to the ball
In `main.tscn`, walls have `collision_layer = 32` (layer 6). Ball's `collision_mask = 37` = layers 1+3+4+6 (1+4+32=37? Let's check: 1=paddle, 2=ball, 4=brick, 32=wall → 1+4+32=37 ✓). This is correct — just worth documenting explicitly like you did for `collision_mask = 0` on paddle.

### 3. `_resolve_round_clear()` can race with `_on_ball_lost()`
There's a 1.2s `await` in `_resolve_round_clear()`. If the last brick drops a ball off-screen during that window, the `_on_ball_lost` guard checks `phase == ROUND_CLEAR` — this *is* guarded. Good. But `_transitioning` is set to true only *inside* `_resolve_round_clear()`, not before the await. A second call before the await could technically slip through the `_transitioning` guard. **Fix**: set `_transitioning = true` as the *first* line.

### 4. `_start_new_run()` doesn't reset `_life_lost_pending`
```gdscript
func _start_new_run(start_level: int = 1) -> void:
    # ...
    _life_lost_pending = false  # ← missing
```
If a run ends mid-deferred call, this flag can persist into a restart.

### 5. Victory triggers at `>= BASE_LEVEL_COUNT`, not `== BASE_LEVEL_COUNT + 1`
```gdscript
if current_level >= LevelDefs.BASE_LEVEL_COUNT:
```
This means clearing level 5 in endless mode (if you somehow re-enter level 5) would also trigger victory. Should be `== BASE_LEVEL_COUNT` or check `current_level == LevelDefs.BASE_LEVEL_COUNT` explicitly.

## 🟡 Gameplay / Mechanics Issues

### 6. `_clamp_min_speed()` can cause permanent horizontal drift
```gdscript
if absf(velocity.x) < 50.0:
    velocity.x = 50.0 if velocity.x >= 0.0 else -50.0
```
A ball traveling purely vertically (`velocity.x == 0`) gets forced to `x = 50`, adding unintended horizontal drift every bounce. Consider only clamping when `velocity.x != 0`, or use a tighter tolerance:
```gdscript
if velocity.x != 0.0 and absf(velocity.x) < 50.0:
    velocity.x = signf(velocity.x) * 50.0
```

### 7. Multiball clones ignore the slow effect on velocity, not just speed
```gdscript
clone.velocity = rotated.normalized() * clone.speed
```
`clone.speed` is correctly set during `_spawn_ball()` when slow is active, but `clone.velocity` is set *after* spawn using `clone.speed` — which is already the slowed value. This is actually fine as written, but it's subtle and fragile. Worth a comment.

### 8. Sticky mode with multiball is surprising
When sticky is active and multiple balls are in play, only the first ball to hit the paddle gets "caught" (due to the `is_instance_valid(stuck_ball)` guard). The other balls bounce normally. This is a reasonable design choice but could confuse players — worth a comment or optional: auto-launch stuck ball when a second ball approaches.

### 9. `_spawn_powerup` cooldown is global, not per-drop-source
If 3 bricks are destroyed nearly simultaneously (common with laser), only 1 powerup can drop per 0.8s. This is intentional to prevent flooding, but the 0.8s window means fast laser play can feel "dry" of powerups. Consider reducing to 0.4s or tying cooldown to powerup *type* rather than all drops.

### 10. Ball `_on_screen_exited` fires for top/side exits too
```gdscript
func _on_screen_exited() -> void:
    if global_position.y > get_viewport_rect().size.y:
```
The y-check guards against premature life-loss. Good. But there's a subtle edge case: if the ball exits the screen at high speed *and* hasn't yet been processed for a frame after the notifier fires, `global_position.y` might not yet exceed the screen height. Adding a small buffer (`+ 20`) would be safer:
```gdscript
if global_position.y > get_viewport_rect().size.y + 20:
```

Both are right-anchored. `EffectList` sits at `offset_top = -140` from the bottom-right, `LivesContainer` sits at `offset_top = 8` from the top-right. On tall effect lists (3-4 active), they won't overlap — but if you ever add a 5th simultaneous effect type, they would. Consider explicitly reserving the top-right for lives and pinning `EffectList` to bottom-right of *center* or adding `max_children` enforcement.
