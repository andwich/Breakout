Session 19 review — focused on launch/transition flow, live play mechanics, and a couple of aesthetic nits. Structured by severity, with concrete fixes.

## Critical

**Multiball + Sticky Paddle: second ball freezes permanently instead of bouncing or being caught**

In `ball.gd`, the paddle-collision branch does this:

```gdscript
if collider is Paddle:
    paddle_hit.emit()
    _pop_visual()
    var p := collider as Paddle
    if p.sticky_mode:
        p.stick_ball(self)
        launched = false
        velocity = Vector2.ZERO
        return
```

But `Paddle.stick_ball()` silently no-ops if a ball is already stuck:

```gdscript
func stick_ball(ball: Ball) -> void:
    if stuck_ball and is_instance_valid(stuck_ball):
        return
    stuck_ball = ball
    ...
```

With Multiball active and Sticky active at the same time, the *first* ball that touches the paddle gets properly caught. Every subsequent ball that touches the paddle that frame or later also gets `launched = false; velocity = Vector2.ZERO` applied to it — but `stick_ball()` rejected it, so the paddle never tracks or repositions it. That ball just sits frozen in space forever: not moving, not scoring, not lost, not visible in `_get_waiting_ball()` logic in any useful way. It silently removes a ball from play without any signal firing.

Fix — only freeze the ball if the catch actually succeeded:

```gdscript
# paddle.gd
func stick_ball(ball: Ball) -> bool:
    if stuck_ball and is_instance_valid(stuck_ball):
        return false
    stuck_ball = ball
    ball.global_position = global_position + Vector2(0, -get_ball_attach_offset())
    queue_redraw()
    return true
```

```gdscript
# ball.gd
if p.sticky_mode:
    if p.stick_ball(self):
        launched = false
        velocity = Vector2.ZERO
        return
    # paddle already has a caught ball — treat this one as a normal bounce
```

(then fall through to the normal reflect-off-paddle logic below instead of `return`ing)

## High

**`ScreenTransition._busy` is read/written directly from `main.gd`, bypassing its own guard and leaving overlay state inconsistent**

Two places touch the autoload's "private" flag directly:

```gdscript
# main.gd — _resolve_round_clear()
while ScreenTransition._busy:
    await get_tree().create_timer(0.1).timeout
ScreenTransition.change_scene("res://ui/victory.tscn")
```

```gdscript
# main.gd — _enter_game_over()
ScreenTransition._busy = false
```

`ScreenTransition` already has a 5-second stuck-guard in `_process()` that resets `_busy` — but the game-over path bypasses it entirely and forces `_busy = false` without calling `_reset_overlay_state()`. If `_busy` got stuck because a fade was mid-flight (overlay still opaque, `mouse_filter = STOP`), this reset unblocks the *flag* but can leave the screen covered by an opaque, input-blocking `ColorRect` with nothing left to fade it back out. Meanwhile the victory path just busy-waits in 0.1s polling for up to 5 seconds if something goes wrong — better than a permanent hang, but still a bad player-facing stall with no feedback.

Suggested fix — give `ScreenTransition` a real public API instead of poking its internals:

```gdscript
# screen_transition.gd
func is_busy() -> bool:
    return _busy

func force_reset() -> void:
    _busy = false
    _guard_timer = 0.0
    _reset_overlay_state()
```

```gdscript
# main.gd
while ScreenTransition.is_busy():
    await get_tree().create_timer(0.1).timeout
ScreenTransition.change_scene("res://ui/victory.tscn")
```

```gdscript
# main.gd — _enter_game_over()
ScreenTransition.force_reset()
```

Small change, but it closes the gap where a stuck transition could leave the whole screen black and unresponsive.

## Medium

**Restarting after Game Over reuses the live scene tree but doesn't clear combo/shake state**

`_restart_run()` → `start_new_run()` → `_start_new_run()` does **not** reload `main.tscn` — it's the same `Main` node being reset in place. It correctly resets score/lives/paddle/slow-factor, but leaves untouched:

- `_combo_count` (if the player died mid-combo, it carries into the new run)
- `_combo_label` (may still be visible/mid-fade)
- `_shake_tween` / `_shake_intensity` (if a shake was still decaying)

So the very first brick hit of a fresh run can silently start from a nonzero combo count, or the old combo label can flash back in.

```gdscript
# main.gd — add to _start_new_run()
_combo_count = 0
_combo_timer.stop()
if _combo_tween and _combo_tween.is_valid():
    _combo_tween.kill()
if _combo_label:
    _combo_label.visible = false
if _shake_tween and _shake_tween.is_valid():
    _shake_tween.kill()
_shake_intensity = 0.0
position = _base_position
```

## Low / Style

- `hud.tscn`: `HighScoreLabel` still has the `text = " "` single-space placeholder from last session's open item — still worth swapping to `text = ""` whenever you're next in that file.
- `title_screen.gd`: the legend-building loop declares `var name := PowerUpRegistry.display_name_for(t)`, shadowing the implicit `Node.name` property. Not a bug (GDScript allows it), but worth renaming to `display_name` for clarity/consistency with the rest of the codebase's naming.

Everything else — laser one-shot scoring, brick `was_already_scored` guard, deferred-launch pattern, score popup camera-shake compensation, screen-transition fade sequencing on scene load — all still look solid and consistent with prior sessions' fixes. The multiball+sticky interaction is the one I'd prioritize; it's a silent, hard-to-notice ball leak that would only show up in exactly the kind of playtesting combo (Multiball + Sticky together) your checklist already flags as a known trouble spot.
