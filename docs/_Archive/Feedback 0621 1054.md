The project already has a strong core: the state-driven structure, synthesized audio, neon theme singleton, and effect-heavy brick/ball work give it a coherent modern-retro identity rather than a bare prototype. The best refinements now are in launch flow consistency, a couple of ball/brick interaction edge cases, and making the baseline visuals feel as considered as the special-case visuals.[1]

## Refinement areas

| Area | What I saw | Risk | Refinement |
|---|---|---|---|
| Launch flow | The app starts from `res://ui/title_screen.tscn`, while the gameplay conductor is `main.gd` on `main.tscn`, and transient session data is stored in `RunState`.[1] | That split can let the “run project” path and “run main scene directly” path drift apart, which matches the repo’s explicit concern about black flashes and startup behavior when `main.tscn` is run directly.[1] | Use a single bootstrap/root scene that always owns transitions and mounts either title or gameplay as children, instead of changing whole scenes between title and play.[1] |
| Scene transitions | `ScreenTransition.change_scene()` fades out, calls `change_scene_to_file()`, waits one frame, then fades in; it also has a 5-second busy guard.[1] | Whole-scene swaps are the most likely place for one-frame empties, overlay timing races, and “why did this launch path behave differently?” bugs.[1] | Keep `ScreenTransition` persistent, but swap child content inside a stable root so the overlay, audio, and stateful managers never disappear during launch/play transitions.[1] |
| Brick hits | In `ball.gd`, brick collision calls `take_damage(1)` and then immediately returns if `collider.is_scored()` is true; in `brick.gd`, `destroy()` sets `_scored = true` before `queue_free()`.[1] | A kill shot can skip the later bounce/pop path in `ball.gd`, and the branch that tries to emit `point_value` for a queued-for-deletion brick is effectively dead after `_scored` becomes true.[1] | Have `take_damage()` return a result such as `{destroyed, awarded_points}`, or decide bounce/score from pre-hit state so the ball always reacts cleanly on the final hit.[1] |
| Ball feel | Launch adds a random `-8..8` degree spread, `attach_to_paddle()` uses a fixed `Vector2(0, -30)`, and paddle rebound uses `(position.x - p.position.x) / (p.target_width / 2.0)`.[1] | The first shot can feel slightly inconsistent, the attach offset may look wrong when paddle size changes, and local-position math is more fragile than global-position math if scene transforms ever change.[1] | Tie attach height to paddle bounds, make randomness optional or smaller for the first serve, and compute rebound from `global_position.x - p.global_position.x` for robustness.[1] |
| Aesthetic depth | The palette is centralized in `GameTheme`, the playfield uses a scanline `BackgroundOverlay`, and boss/metal bricks get extra shader treatment while standard bricks fall back to flat `row_color` fills.[1] | Special bricks look authored, but standard rows can read flatter than the rest of the scene, which makes the visual hierarchy feel uneven.[1] | Give normal bricks a lightweight shared glow/rim treatment or subtle per-row emissive pulse so the whole field matches the quality level of boss/metal bricks.[1] |

## Gameplay feel

The biggest gameplay fix is the brick-destruction collision path, because it can affect both scoring semantics and whether the ball visually/physically “answers” a final hit the same way it answers a nonlethal hit. I would treat that as priority one, ahead of tuning, because once collision feedback is deterministic, changes to launch angle, sticky release, laser overlap, and combo feel become much easier to judge.[1]

A smaller but worthwhile polish pass is the stuck/launch lifecycle: `_last_pos` and related recovery logic are present, but initializing those values when the ball is attached or relaunched would make the escape heuristic more intentional and easier to reason about. That is the kind of invisible cleanup that usually reduces “rare weirdness” more than it changes normal play feel.[1]

## Visual direction

The current style language is good: dark neon background, scanlines, glow shaders, particles, and punchy HUD animation all point in the same direction. The next step is not “more effects everywhere,” but better distribution of quality so ordinary bricks, title-to-play transitions, and serve moments feel as premium as boss hits and power-up moments.[1]

One strong aesthetic upgrade would be to make launch moments feel ceremonial: brief paddle underglow, a tighter “ready” pulse, and a cleaner first-ball spawn alignment would make the start of each life feel deliberate rather than just functional. That would reinforce the arcade identity without changing any mechanics.[1]

## Priorities

1. Fix the brick kill-shot collision flow so final hits still produce the intended bounce/feedback behavior.[1]
2. Unify title/game startup under one persistent root to eliminate launch-path drift and transition artifacts.[1]
3. Normalize ball serve feel by reducing gratuitous randomness and making paddle-relative math/bounds explicit.[1]
4. Add a low-cost glow treatment for standard bricks so the full board matches the polish of the special bricks.[1]

My short verdict: the game looks structurally sound and stylistically coherent, but it would benefit most from one architecture cleanup around startup and one gameplay cleanup around ball-vs-brick resolution. After those, the remaining work is mostly feel and finish rather than foundation.[1]

## `main.gd`

The repo documentation says `main.gd` is the run conductor and should own phase transitions, while UI renders state. The strict goal here is not a big rewrite, but centralizing all run-entry setup so title-start, restart, and direct-run behavior stop drifting.[1]

- Add one canonical session entry function: `start_new_run(start_level: int = 1) -> void`.[1]
- Move score/lives/phase/level-reset work that currently happens in scattered handlers into that function.[1]
- Any title-start or restart button path must call that function, directly or indirectly.[1]
- Do not let `title_screen.gd` own play-state initialization.[1]

func start_new_run(start_level: int = 1) -> void:
