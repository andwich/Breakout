### Launch / Scene Management

**[HIGH] `_start_level_intro` — boolean `_intro_running` is still not race-condition proof**

The existing fix from Session 11 (set `_intro_running = false` before scene change) is present, and the `_resolve_round_clear` path correctly sets it before the victory scene swap. But the boolean still has a window: if `_load_level` is called a second time while the first `await _intro_timer.timeout` is still suspended (e.g. rapid level-clear during the 1.2s `ROUND_CLEAR` wait), the second call sets `_intro_running = true`, then the first coroutine resumes and passes the `if not _intro_running` guard — and both coroutines proceed to `_begin_ready_phase()`, double-spawning a ball.

The `_transitioning` flag does gate `_resolve_round_clear`, but `_load_level` is also called from `_start_new_run`, and any future call path that skips that gate would silently re-expose the bug. A generation counter is strictly safer:

```gdscript
var _intro_gen: int = 0   # replace _intro_running: bool

func _start_level_intro() -> void:
    _intro_gen += 1
    var my_gen := _intro_gen
    phase = GameState.Phase.LEVEL_INTRO
    hud.show_level_intro(_level_title_text(), _level_subtitle_text())
    await get_tree().create_timer(1.0).timeout
    if _intro_gen != my_gen:   # stale: a newer intro was started
        return
    if not is_inside_tree():
        return
    hud.hide_level_intro()
    _begin_ready_phase()
```

This removes `_intro_running` entirely and eliminates the boolean-race window.

**[MEDIUM] `_load_level` clears `_intro_timer` but the old `SceneTreeTimer` keeps running**

```gdscript
_intro_running = false
_intro_timer = null     # <-- only clears the reference
```

`SceneTreeTimer` cannot be cancelled — nulling the variable doesn't stop the timer. The old timer will still fire its `timeout` signal, and if another `await _intro_timer.timeout` is parked on a fresh timer with the same variable name, the stale timer firing first is invisible but can corrupt timing on fast replays. The generation counter above handles this without needing a cancellable timer.

**[LOW] `ScreenTransition.change_scene` `_busy` guard silently swallows calls**

In `_resolve_round_clear`, if `ScreenTransition._busy` is true (e.g. from a rapid-restart edge case), the `change_scene` call returns immediately and the game enters `VICTORY` phase permanently with no scene loaded. There's no fallback or log. A deferred retry or at minimum a `push_warning` would surface this in development:

```gdscript
if not await ScreenTransition.change_scene("res://ui/victory.tscn"):
    push_warning("ScreenTransition busy; victory scene not loaded")
```

Since `change_scene` returns `void`, the practical fix is checking `ScreenTransition._busy` before calling, or resetting it in `_enter_game_over`.

### Play Mechanics

**[HIGH] `ball.gd` — `_clamp_min_speed` is called after every wall/ceiling bounce but NOT after the brick collision branch**

Look at the collision handler structure:

```gdscript
if collider is Brick:
    collider.take_damage(1)
    if collider.is_scored():
        return      # <-- early return, no bounce, no clamp — correct
    ...
    _pop_visual()
    # falls through to the bounce below? NO — no explicit bounce here

if collider is Paddle:
    ...
    return
else:
    velocity = velocity.bounce(normal)
    _clamp_min_speed()
```

The `if collider is Brick` block does **not** `return`, so execution falls through to the `if collider is Paddle / else` block. On a brick hit where `is_scored()` is false, `collider` is a `Brick`, not a `Paddle`, so the `else` branch fires — `velocity.bounce(normal)` and `_clamp_min_speed()` do run. This is actually correct behavior, but the control flow is genuinely confusing and fragile. If anyone adds a `return` after `_pop_visual()` during a refactor (which looks natural), the bounce stops happening and balls pass through bricks silently. An explicit `velocity = velocity.bounce(normal); _clamp_min_speed()` inside the brick branch would make intent clear:

```gdscript
if collider is Brick:
    collider.take_damage(1)
    if collider.is_scored():
        return
    if not collider.is_queued_for_deletion():
        brick_hit.emit(1)
    else:
        brick_hit.emit(collider.point_value)
    velocity = velocity.bounce(normal)   # explicit
    _clamp_min_speed()                   # explicit
    _pop_visual()
    return                               # explicit — don't double-bounce
```

Without this the ball will double-bounce (brick branch falls into the else), which changes the angle. This is a latent correctness bug, not just a style issue.

**[HIGH] `_on_brick_destroyed` is connected via `on_destroyed` callable, but `_drops_this_frame` resets in `_physics_process` — signal timing mismatch**

`_drops_this_frame` is reset to `0` in `_physics_process`. `brick.destroyed` is emitted from `brick.destroy()`, which is called from `take_damage`. `take_damage` is called from inside physics callbacks (`ball._physics_process`, `laser._physics_process`). All three paths run in the same physics frame, so multiple bricks destroyed in one frame correctly share the `_drops_this_frame` counter — the fix from Session 14 is working as intended. ✅ Confirmed resolved.

**[MEDIUM] Multiball clone speed after slow restore**

When `_restore_ball_speeds` runs, it iterates `balls_container` and sets each ball's `speed` to `base_speed * speed_mult`. But multiball clones were spawned with `clone.speed` already set by `_spawn_ball` (which applies `_slow_factor` at spawn time). After restore, `clone.speed` is correctly updated in the loop — but `clone.base_speed` is the same as the original ball's `base_speed`, so the math is right. ✅ No bug here, but it's worth noting that if `base_speed` were ever per-ball (e.g. for a speed power-up), this loop would need updating.

**[MEDIUM] `_on_ball_lost` phase guard missing `ROUND_CLEAR` deferred window**

The guard correctly lists `ROUND_CLEAR` as a blocked phase. But there's a subtle gap: `_resolve_round_clear` sets `phase = ROUND_CLEAR` only after the `if phase != PLAYING or _transitioning` check passes. Between the last brick being destroyed (emitting `destroyed`) and `_resolve_round_clear` setting `ROUND_CLEAR`, the phase is still `PLAYING`. If a ball exits the bottom in that same frame (before the deferred `_process_life_loss` runs), `_on_ball_lost` passes its guard and queues a life loss. The `_has_active_ball()` check partially mitigates this, but a ball that was just queued for deletion still exists in `balls_container` and returns true from `is_Ball`. The safest fix is setting `phase = ROUND_CLEAR` as the very first line of `_resolve_round_clear` before any `await`:

```gdscript
func _resolve_round_clear() -> void:
    if phase != GameState.Phase.PLAYING or _transitioning:
        return
    phase = GameState.Phase.ROUND_CLEAR   # move this up
    _transitioning = true
    ...
```

**[LOW] `_disable_sticky` in `paddle.gd` launches the stuck ball during pause**

func _disable_sticky() -> void:
    sticky_mode = false
    sprite.color = Color(0.2, 1.0, 1.0)
    if stuck_ball and is_instance_valid(stuck_ball):

This is an edge case but worth noting; adding a `main.phase == PLAYING` check would be more robust than relying on `get_tree().paused`.

### Aesthetic Quality

**[HIGH] Double-bounce produces wrong reflection angle on brick hits**

This is the mechanical consequence of the control flow bug called out above. When a ball hits a brick and `is_scored()` is false, the brick branch falls through to the `else` (since `Brick` is not `Paddle`), executing `velocity.bounce(normal)` once. This single bounce is correct, but because the `if collider is Brick` block doesn't `return`, and the `else` is `else` of `if collider is Paddle` — not of `if collider is Brick` — the bounce only happens once. Actually re-reading carefully: the structure is:

```gdscript
if collider is Brick:   # A
    ...
    _pop_visual()

if collider is Paddle:  # B — separate if, not elif
    ...
    return
else:                   # else of B
    velocity = velocity.bounce(normal)
    _clamp_min_speed()
```

Since A and B are separate `if` statements, when a brick is hit: A runs (no return for non-scored brick), then B runs (`Brick` is not `Paddle` → else branch) → bounce happens. So the bounce is happening once. The issue is that **`_pop_visual` plays before the bounce**, and there's no return, meaning if the ball happens to also be touching a wall or paddle in the same substep (edge case), double processing occurs. More practically: the lack of `return` after the brick block means the ball can bounce and then be re-processed by the paddle check in the same frame. Adding `return` after the brick's `_pop_visual()` call (and doing the bounce explicitly before it, as shown above) eliminates the ambiguity entirely.

**[MEDIUM] Score popup coordinate space — camera shake causes visible drift**

The Session 14 fix uses `get_viewport().get_canvas_transform() * world_pos`. This is correct when `Main` (Node2D) has no transform applied. But `_shake_camera` modifies `position` on the `Main` node itself, which shifts the world-to-canvas mapping. `get_canvas_transform()` reflects the viewport's canvas transform, not the node's local shake offset. So during shake, popups will appear offset from the brick they originated from. The cleanest fix is to add popups to a `CanvasLayer` (which ignores node-tree transforms), or to compensate for `position` offset:

```gdscript
# Option A: add popup to HUD's CanvasLayer (already immune to shake)
# The label is already added to hud — but hud is a CanvasLayer,
# so world_pos needs converting to canvas space correctly.

# The actual issue: Main.position offset from shake is NOT included
# in get_canvas_transform(). Use:
var screen_pos := get_viewport().get_canvas_transform() * (world_pos + position - position)
# No — the fix is:
var canvas_xform := get_viewport().get_canvas_transform()
# Main's shake offset shifts world coords; undo it:
var corrected_world := world_pos - position  # remove shake translation
var screen_pos := canvas_xform * corrected_world
```

Wait — `get_canvas_transform()` maps world-space to screen-space, and `Main.position` IS part of the world transform of children. Since brick `global_position` is already in world space (unaffected by Main's position jitter... actually it is affected because bricks are children of `bricks_container` which is a child of `Main`). So when `Main` shakes, bricks move in world space too, meaning `global_position` of a brick already includes the shake. The `canvas_transform` converts that shaken world pos to screen correctly. The popup should actually appear at the right place. This one may be a non-issue — worth testing visually but the math appears consistent.

**[MEDIUM] Combo label position jitter — `get_minimum_size()` called immediately after `reset_minimum_size()` and font size override**

```gdscript
_combo_label.add_theme_font_size_override("font_size", size_override)
_combo_label.reset_minimum_size()
_combo_label.position = Vector2(
    (get_viewport_rect().size.x - _combo_label.get_minimum_size().x) / 2.0,
    ...
)
```

`reset_minimum_size()` invalidates the cached minimum size and queues a layout update, but `get_minimum_size()` called immediately after on the same frame may return the stale (pre-resize) value because layout hasn't been flushed. The fix is to use `await get_tree().process_frame` before reading the size, or to calculate based on the font size directly. A simpler approach: set `anchors_preset = PRESET_CENTER` and let the Control system center it automatically instead of manual positioning.

**[LOW] `powerup.gd` — `rotation += delta * 1.2` rotates the full `Area2D`, distorting the `CollisionShape2D`**

Rotating an `Area2D` with a `RectangleShape2D` child rotates the collision shape too, making it a rotated rectangle. For a small square this produces minimal gameplay difference, but it's technically wrong — the hitbox becomes a diamond at 45°. The visual `Sprite` (ColorRect child) should be the only thing rotating. Either move rotation to the `$Sprite` node only, or use a `CircleShape2D` (rotation-invariant) for the collision:

```gdscript
# In _physics_process, rotate only the visual child:
$Sprite.rotation += delta * 1.2
# (remove: rotation += delta * 1.2 from the Area2D itself)
```
